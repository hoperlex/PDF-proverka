# Runbook: диагностируемый test harness

**Владелец:** OPS.<br>
**Задача-источник:** `W0-OPS-03` (части 1 и 2).<br>
**Контракт:** [quality/runtime contract v1](../architecture/QUALITY_RUNTIME_CONTRACT_V1.md),
разделы §3.3, §5, §6, §7, §8.<br>
**Редакция:** 2026-08-31.

## 0. Что этот harness обещает и чего не обещает

Обещает три вещи:

1. **Зависание становится диагностируемым отказом.** Тест, вышедший за
   бюджет, даёт node ID, дамп всех потоков, инвентарь дочерних процессов,
   запись `<failure type="timeout">` в JUnit и ненулевой код возврата.
   Молчаливого cancel или skip не бывает.
2. **Отчёт свежий или его нет.** Старый JUnit удаляется до прогона; после
   прогона проверяются существование, mtime и разбираемость. Любой из трёх
   отказов — infrastructure failure, даже если pytest вернул ноль.
3. **Отсутствие обязательного входа — явная причина отказа, а не смена
   baseline.** Без provisioned norm corpus `--record` не выполняется.

**Не обещает:** ничего не включает в enforce. Workflow, `pytest.ini` и
root-зависимости принадлежат `W0-INT-01`; до его выполнения весь harness —
observe-only инструмент, который запускают руками.

## 2. Обычный прогон одного lane

```bash
python scripts/ci_test_lane.py --lane unit
python scripts/ci_test_lane.py --lane contract
python scripts/ci_test_lane.py --lane integration
python scripts/ci_test_lane.py --lane network
python scripts/ci_test_lane.py --lane chaos
```

Раннер сам запускает capability probe перед pytest (§6). Если probe отказал,
pytest **не запускается** — это setup failure, а не повод для skip.

Полезные флаги:

| Флаг | Когда нужен |
| --- | --- |
| `--skip-probe` | локальная отладка на машине, заведомо не проходящей probe (например под root) |
| `--paths <путь>` | прогнать один модуль вместо всего набора |
| `-m <выражение>` | выбрать маркеры |
| `--per-test-timeout N` | **только вниз**, для быстрого воспроизведения зависания |
| `--json` | receipt на stdout; вывод pytest при этом уходит в stderr, чтобы stdout остался чистым JSON |

Все четыре артефакта канонически принадлежат паре «(lane, вид)»: прогон
одного lane не может писать в артефакт другого lane или в артефакт другого
вида — такая попытка отклоняется ДО удаления файла, с ненулевым кодом.

Артефакты именуются по файлу отчёта, а не по имени lane: прогон со своим
`--junit` не затрёт журнал штатного прогона того же lane. Два одновременных
прогона с одинаковым `--junit` по-прежнему конфликтуют — это осознанное
ограничение, в CI один job запускает один lane.

Увеличивать бюджет, чтобы «перестало падать», контрактом запрещено (§7:
«Увеличение timeout для сокрытия deadlock не принимается»). Исключение
оформляется node ID, измеренным p95, новым лимитом, владельцем и сроком.

## 3. Коды возврата раннера

| Код | Значение | Что делать |
| ---: | --- | --- |
| 0 | все тесты прошли, отчёт свежий | ничего |
| 1 | тесты падают | разбирать падения |
| 2 | probe не пропустил lane | чинить окружение, **не** запускать lane |
| 3 | исчерпан per-test или wall бюджет | §4 ниже |
| 4 | отчёт missing / stale / unparseable, либо pytest оборван | §5 ниже |
| 5 | выборка пуста — не собрано ни одного теста | проверить `--paths` и `-m` |

Коды 2–5 означают «прогон непригоден для выводов». Считать такой прогон
зелёным нельзя ни при каких обстоятельствах.

Код 5 отделён от 4 намеренно: при пустой выборке отчёт как раз исправен,
пуста именно выборка. Общий код отправил бы дежурного искать повреждённый
XML, которого нет.

## 4. Разбор таймаута (код 3)

1. Прочитать `.ci/reports/<lane>.timeout.json`. Там уже лежит всё нужное:
   `nodeid`, `budget_seconds`, `elapsed_seconds`, `children` (инвентарь
   дочерних процессов), `child_cleanup` и `thread_dump`.
2. В дампе искать поток, стоящий на строке теста. Он и есть место зависания.
3. Дочерние процессы harness добивает сам лестницей SIGTERM → SIGKILL, но
   инвентарь сохраняет: если ребёнок был, зависание почти всегда в ожидании
   его вывода. Обход рекурсивный — снимаются и внуки (`depth` в инвентаре
   показывает уровень), иначе связка «тест → uvicorn → воркер» оставляла бы
   воркера с `ppid=1`, а тот держал бы порт и валил следующий job. Группа
   процессов добивается ещё и снаружи, раннером: между обходом `/proc` и
   выходом зависший тест успевает породить ещё один процесс.
4. Воспроизвести точечно:
   `python scripts/ci_test_lane.py --lane <lane> --paths <файл> --per-test-timeout 10`.

**Бюджет считается на узел целиком.** Отсчёт идёт от начала `setup` до конца
`teardown`, а не только на тело теста: зависание в фикстуре — такое же
зависание. Практическое следствие: поднятие session-scoped фикстуры попадает в
бюджет ПЕРВОГО теста, который её затребовал. Если таймаут указывает на
безобидный с виду первый тест модуля, смотреть надо на его фикстуры, а не на
тело.

**Первый таймаут останавливает lane.** Watchdog снимает процесс, поэтому до
остальных тестов дело не доходит. Это следствие §7 («Hang никогда не
превращается в молчаливый cancel или skip»), а не недосмотр: зависание — отказ
окружения, и продолжать прогон на нём значит собирать недостоверные
результаты. Чинить нужно первый названный узел, затем запускать снова.

**Wall-бюджет lane.** Если исчерпан общий бюджет, а не бюджет теста, дамп
изнутри pytest недоступен: процесс снят снаружи. Node ID активного теста
harness всё равно определяет по журналу событий и кладёт в receipt. Для дампа
повторить прогон с меньшим `--per-test-timeout`.

### 4.1. Что harness публикует о дочерних процессах

Командная строка НЕ публикуется. Вместо неё — структура, безопасная по
построению (P-13: разрешено то, что явно разрешено, а не то, что не
запрещено):

| Поле | Что содержит |
| --- | --- |
| `comm` | имя из `/proc`, если оно есть в списке обычных программ; иначе `<comm>` — процесс задаёт `comm` себе сам через `prctl` |
| `cmdline` | разрешённый basename executable, точно allowlisted имена флагов, доменно-безопасные значения, счётчики скрытого и отпечаток |
| `argc` | полное число аргументов |
| `positional_count` | сколько позиционных аргументов скрыто |
| `hidden_flag_count` | сколько неизвестных имён флагов скрыто |
| `argv_fingerprint` | HMAC-SHA256 argv со СЛУЧАЙНЫМ ключом прогона |

Имя флага видно только если оно точно перечислено в `SAFE_FLAG_NAMES`:
одной конвенционной формы недостаточно, opaque-секрет тоже может выглядеть
как `--lowercase-name`. Значение точно allowlisted флага публикуется, только если
оно также проходит доменную проверку из `SAFE_VALUE_FLAGS`. Всё остальное
не публикуется.

Как это выглядит:

```text
python3 -m=uvicorn --host=127.0.0.1 --port=8081 --reload
    [1 позиционных] argv:8ce9c9ba1d4e77a2
```

Цена названа честно: по `cmdline` больше нельзя прочитать, какой файл
обрабатывал зависший процесс. Опознать процесс по-прежнему можно — по
безопасному basename, набору флагов и `comm`; сличить два процесса или два
процессы внутри одного прогона — по `argv_fingerprint`; понять, сколько
сведений скрыто, — по счётчикам.

Отпечаток сравним ТОЛЬКО внутри одного прогона: ключ случаен и не переживает
процесс. Обычный SHA-256 здесь не годится — у argv низкая энтропия, и значение
восстанавливается перебором словаря (измерено: `--pin 0427` за 10 000 попыток).

Дамп потоков публикуется без каталогов: от пути остаётся имя файла, номер
строки и функция. Каталоги несут идентификаторы проекта и клиента, а на вопрос
«где зависло» отвечает имя файла. Текст падения (`longrepr`) в журнал не
пишется вовсе: Bible считает traceback непроверенным вводом, а потребителя у
этого поля не было.

Правило — `scripts/ci_redaction.py`, применяется в источнике, внутри обхода
`/proc`. Сырого argv не существует ни в JUnit, ни в журнале событий, ни в
диагностике таймаута.

Границы честно: harness публикует безопасно то, что публикует САМ. Текст
падений и traceback'и пишет в свой JUnit сам pytest, и их обработка — не
свойство этого harness.

### 4.2. Ограничение тестового контракта: node ID

§7 требует печатать полный pytest node ID, и pytest публикует его в своём
JUnit независимо от harness. Скрыть его нельзя — тогда таймаут перестанет быть
диагностируемым. Отсюда ограничение, адресованное **автору теста**, а не
harness:

> Параметризованный node ID не должен строиться из секретных данных.
> `@pytest.mark.parametrize("token", [REAL_TOKEN])` публикует этот токен в
> имени теста — в отчёте, в baseline и в логе job'а.

Ограничение проверяемое, а не декларативное. Команда берёт из собранных node
ID только параметрическую часть — ту, что строится из данных, — и прогоняет её
через то же правило, что защищает свободные поля:

```bash
python -m pytest tests backend/tests --collect-only -q -p no:cacheprovider \
  | PYTHONPATH=scripts python3 -c '
import re, sys
from ci_redaction import redact_text
param = re.compile(r"\[(.+)\]\s*$")
bad = [l.rstrip() for l in sys.stdin
       if (m := param.search(l.rstrip())) and redact_text(m.group(1)) != m.group(1)]
print("\n".join(bad) if bad else "параметрических ID с секретами не найдено")'
```

Проверяется именно `[...]`, а не имя целиком: имена классов и функций пишет
разработчик, данные приходят из `parametrize`. Без этого сужения правило блоба
ловит длинные CamelCase-имена вроде
`TestPolicyV3SourceDependencyAndEvidenceChecked`, и вывод становится
неразбираемым — измерено, 109 срабатываний против 9 по существу.

Замер на 2026-08-31: **9 срабатываний**, все в `test_distributed_workers_agent`
и `test_distributed_workers_hardening` — это тесты самой redaction, и их
параметры являются синтетическими секретами по назначению. Ожидаемый профиль:
модуль, проверяющий вырезание секретов, обязан их содержать. Появление
срабатывания в ЛЮБОМ другом модуле — повод разобраться до того, как имя уедет
в отчёт и baseline.

Проверка эшелонированная: она ловит известные формы, а не доказывает
отсутствие секретов.

## 5. Разбор непригодного отчёта (код 4)

| `report_status` | Что произошло | Причина |
| --- | --- | --- |
| `missing` | JUnit не создан | pytest умер на сборе; смотреть stderr |
| `stale` | mtime старше старта прогона | pytest не дописал отчёт; отчёт от прошлого раза не засчитывается |
| `unparseable` | XML не разбирается | прогон оборван на записи |

Во всех трёх случаях сравнивать с baseline нельзя. Отчёт прошлого прогона
**никогда** не переиспользуется — на это стоит отдельная проверка mtime.

## 6. Norm corpus

```bash
python scripts/ci_provision_norms.py --check --json     # состояние
python scripts/ci_provision_norms.py --build-index      # собрать индекс
python scripts/ci_provision_norms.py --check --enforce  # режим enforce CI
python scripts/ci_provision_norms.py --digest PATH      # SHA-256 дерева корпуса

# Получение из внешнего источника (так это делает CI):
python scripts/ci_provision_norms.py --acquire --build-index --enforce-if-configured --json
```

Источник задаётся только конфигурацией (`QR_NORM_ARTIFACT_SOURCE_ID`, `_URL`,
`_VERSION`, `_SHA256`, secret `_TOKEN`), в workflow адрес не зашит. Пока
переменные не заданы, поведение прежнее; как только заданы — любой сбой
получения setup failure. Что обязан предоставить владелец источника, как это
проверяется на свежем non-root раннере и какой код отказа что означает —
[форма приёмки источника](NORM_ARTIFACT_SOURCE.md).

Правила §3.3, реализованные буквально:

- в enforce CI отсутствие `norms/vault/**`, отсутствие ожидаемой контрольной
  суммы, её несовпадение или отсутствие `norms/tools/status_index.json` —
  **setup failure**, ненулевой код возврата. Skip недопустим;
- локально корпус может быть не выбран. Тогда результат помечается
  `OPTIONAL_NORM_CORPUS_ABSENT`, и это не ошибка — но такой прогон **не
  создаёт baseline и не является G0 receipt**;
- `python scripts/ci_regression_gate.py --record` без provisioned корпуса
  отказывает ДО прогона. Обхода нет намеренно: без корпуса часть тестов
  уходит в skip, и запись увековечила бы состояние конкретной машины как
  эталон проекта.

Ожидаемая контрольная сумма берётся из `QR_NORM_ARTIFACT_SHA256` либо из
`norms/vault.sha256` / `norms/norm_artifact.sha256`.

## 7. Инвентарь разметки lanes

```bash
python scripts/ci_lane_inventory.py            # сводка
python scripts/ci_lane_inventory.py --json     # машинный отчёт
python scripts/ci_lane_inventory.py --evidence-sha256   # воспроизводимый отпечаток
python scripts/ci_lane_inventory.py --fail-on-unmarked   # будущий enforce
python scripts/ci_lane_inventory.py --samples 20         # больше примеров конфликтов
```

По §5 каждый test node обязан иметь **ровно один** primary lane marker;
`slow` — ортогональный атрибут, не lane. Непомеченный узел и узел с двумя
primary-маркерами — inventory failure.

Текущее устойчивое утверждение: primary lane marker есть только у
13 test-функций; остальные не размечены. Абсолютные счётчики
хранятся только в
[`W0-OPS-03-part2.json`](../architecture/receipts/W0-OPS-03-part2.json) вместе с
tree-хэшами входов и воспроизводимым evidence SHA-256.

Часть выводов принципиально не делается статически: если тест зовёт функцию
`backend/`, которая сама открывает сокет, признака в тесте нет. Такие модули
инструмент помечает отдельно (`DYNAMIC_DISPATCH`, `KILL_WITHOUT_RESTART`,
`PATCHED_API`, `INHERITED_ONLY`), а не угадывает.

По умолчанию инструмент observe-only и возвращает 0: разметка тысяч узлов —
отдельное решение, а не побочный эффект запуска инвентаря. `--fail-on-unmarked`
включает `W0-INT-01` после того, как разметка выполнена.

## 7.1. Бюджет регресс-гейта

`scripts/ci_regression_gate.py` ограничен по времени: по умолчанию 1800 с,
переопределяется `CI_GATE_WALL_BUDGET_SEC`. Превышение — отказ с ненулевым
кодом, а не бесконечное ожидание; группа процессов добивается лестницей
SIGTERM → SIGKILL, осиротевший pytest не остаётся.

Гейт не даёт per-test диагностики: какой именно тест завис, показывает
lane-раннер, у которого есть бюджет на каждый тест
(`python scripts/ci_test_lane.py --lane unit`). Отказ гейта об этом прямо
сообщает.

Потолок выбран с запасом: наблюдённые времена полного прогона — 335–500 с в
зависимости от загрузки машины. Бюджет, который снимает здоровые прогоны,
выключат, и сторожа не станет вовсе.

## 8. Что запрещено до `W0-INT-01`

- править `.github/workflows/**` — там же снимается `continue-on-error`;
- править `pytest.ini`, в том числе регистрировать маркеры и менять `addopts`;
- править `requirements*.txt` и frontend-манифесты;
- запускать `ci_regression_gate.py --record` на машине, не удовлетворяющей
  clean-room профилю (§3), даже если provisioning прошёл;
- объявлять отказ sandbox по capability продуктовой регрессией.

## 9. Известные ограничения окружения

- **Прогон под root.** `probe --profile network|chaos` отказывает по
  `USER_IS_ROOT`. Это верный отказ: lanes требуют non-root. Для локальной
  отладки — `--skip-probe`, но результат такого прогона не является приёмкой.
- **Активный `.env`.** Импорт конфигурации подхватывает репозиторный `.env`,
  и provider-секрет оказывается в окружении pytest (находка OPS03-F1).
  Обход на время прогона — `AUDIT_DISABLE_DOTENV=1`. Настоящая изоляция —
  §3.2, владелец `W0-INT-01`.
- **`/proc` обязателен** для инвентаря дочерних процессов. Вне Linux список
  будет пустым; harness помечает это полем `proc_available`, а не делает вид,
  что детей не было.
