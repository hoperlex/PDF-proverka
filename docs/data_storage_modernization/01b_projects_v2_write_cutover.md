# Этап 1б. Переключение канонической записи на `projects_v2`

> Этап 1б закрывает разрыв между правилами идентичности этапа 1 и единым
> файловым контуром этапа 2. Он не переносит файлы в S3 и не подключает
> source adapters.

**Статус:** запланирован, не начат; production остаётся в
`dual_write_shadow`.

**Редакция:** 2026-08-27.

## 1. Почему это отдельный этап

Новый файловый контур этапа 2 требует, чтобы принятую версию можно было
атомарно опубликовать в
`projects_v2` и считать её канонической. Сегодня это условие не выполнено:

- `AUDIT_PROJECTS_V2_WRITE_MODE=dual_write_shadow`;
- авторитетная запись идёт в legacy `projects/`;
- `projects_v2` является проверяемым зеркалом;
- полный write-cutover в production не выполнялся;
- действующий playbook имеет статус «ПОДГОТОВКА» и открытые блокеры.

Cutover не прячется внутри S3-миграции: переключение выделено в этап 1б с
собственными владельцами, сроком, критериями завершения и rollback. Это
позволяет проектировать сегменты 2.0–2.2 параллельно, но запрещает включать
новую production-запись до готовности канонического v2-контура.

## 2. Коротко о результате

После этапа 1б:

- `projects_v2` является единственным каноническим контуром записи документов и
  версий;
- обычное чтение, аудит, export, prepare, batch и resume работают из v2;
- legacy не принимает новых авторитетных записей и остаётся временной
  неавторитетной rollback-копией;
- завершённый run публикуется в `runs/<run_id>`, а `latest` воспроизводимо
  строится из выбранного run;
- ошибки legacy-зеркала не меняют канонический результат v2;
- rollback проверен до включения production-записи этапа 2.

Для пользователя это не новый экран. Главное изменение — одна и та же версия
видна во всех разделах, а результат больше не зависит от того, какой backend
первым прочитал legacy или v2.

## 3. Текущий статус и владельцы

| Поле | Состояние на 2026-08-26 |
| --- | --- |
| Production read backend | legacy с частичными v2-представлениями |
| Production write mode | `dual_write_shadow` |
| Полный `projects_v2_primary` | не выполнялся |
| Playbook | 2026-06-18, статус «ПОДГОТОВКА» |
| Владелец cutover | не назначен — блокер |
| Владелец maintenance-окна | не назначен — блокер |
| Владелец rollback/backup | не назначен — блокер |
| Дата решения | не назначена — блокер |
| Период наблюдения после cutover | не утверждён — блокер |

До назначения владельцев допускаются аудит кода, тесты и закрытие технических
блокеров. Production-флаги не переключаются автоматически.

## 4. Открытые блокеры cutover

Перед cutover должны быть закрыты и подтверждены тестами семь пунктов. Первые
шесть происходят из действующего playbook; седьмой найден при повторной
инвентаризации production-писателей 2026-08-26:

1. **Чтение источников стадий из v2.** Pipeline должен находить PDF, MD, HTML,
   result и blocks в `01_input/02_work`, а не ожидать legacy-имена в корне.
2. **Promotion run → latest.** Завершённый `03_analysis/runs/<run_id>` должен
   воспроизводимо и атомарно становиться выбранным `latest`.
3. **Export ZIP.** Export читает PDF из `01_input` и результаты из выбранного
   v2-run.
4. **Destructive-контракт.** Clean, rename и delete либо безопасно работают с
   backup/confirmation, либо явно остаются заблокированными.
5. **Prepare и batch queue.** Все операции сохраняют точные `document_uid` и
   `version_id` и не возвращаются к legacy-пути.
6. **Основной read-path.** `production_uses_v2()` и обычные сервисы читают
   write-backed данные из v2 без скрытого legacy fallback.
7. **Manifest у каждого producer версии.** Живой endpoint
   `POST /api/projects/register-external` вызывает
   `project_service.register_external_project`, который сейчас создаёт
   `project_info.json`, но не `input_manifest.json`. Общий writer должен быть
   подключён и сюда; новая версия без manifest не может быть опубликована.

Список не считается закрытым по наличию кода. Для каждого пункта нужны тест,
canary-сценарий и ссылка на результат проверки.

## 5. Минимальный входной гейт из этапа 1

Этап 1 задаёт полный смысл данных, но этап 1б не ждёт завершения всех его работ.
Для файлового cutover нужен только storage-facing минимум из Работ 3, 6, 7 и 9.

До переключения должны быть готовы минимум:

- постоянная идентичность документа и версии во всех production-писателях;
- единая функция обновления канонического current и его зеркала;
- запрет изменения завершённого run;
- связь `job_id → attempt_id → run_id` и канонический `version.json.run_id`;
- manifest-инварианты: известный `schema_version`, запрет current/complete без
  валидного manifest;
- storage-facing отчёт целостности без необъяснённых critical/error;
- карта legacy → v2 и проверка отсутствия неоднозначных документов.

После достижения этого минимума параллельно могут продолжаться `finding_uid` и
переключение его потребителей, бэкфилл 6440 исторических решений, UI-правки и
строгие ограничения Фазы E. Они не блокируют cutover, если storage-facing
проверки выше зелёные. Этап 1б также не ждёт PostgreSQL или собственного S3.

## 6. Все production-писатели должны пройти через v2-контракт

Перед cutover составляется реестр операций, которые создают или меняют:

- документ;
- версию;
- входной файл;
- `document.json` и `version.json`;
- current pointer;
- run и `latest`;
- review-слой;
- сравнение;
- manifest входного комплекта.

Для каждой операции фиксируются старый писатель, новый v2-писатель, режим
ошибки и тест. Обход storage facade прямой записью в legacy для production-кода
после cutover запрещён.

Отдельно фиксируется найденный producer без manifest:

```text
POST /api/projects/register-external
  → project_service.register_external_project
  → копирование PDF/MD/result/OCR
  → project_info.json
  → сегодня: нет input_manifest.json
```

До cutover он переводится на тот же классификатор, fingerprint и атомарный
manifest writer, что browser upload. Production-публикация считается успешной
только после записи и повторного чтения manifest. Оставлять endpoint открытым и
параллельно ремонтировать историю нельзя: тогда число версий без manifest
продолжит расти.

Специализированные генераторы и миграционные скрипты могут существовать, но их
результат проходит общую schema-валидацию и не создаёт второй канонический
формат.

### 6.1. Manifest и provenance merge исправляются до cutover

Текущий `version_service._v2_merge_collect_source_files` намеренно исключает
`input_manifest.json`, а регресс-тест фиксирует отсутствие manifest в новой
версии. Это уже создаёт необратимую потерю происхождения и не должно ждать
внешнего импорта или schema 2.

До cutover общий writer создаёт для target-версии новый `input_manifest.json`,
пересчитывает состав и SHA-256 и записывает:

```text
derived_from_version.source_document_uid
derived_from_version.source_version_id
derived_from_version.source_manifest_sha256
derived_from_version.source_import_id   # если был
derived_from_version.operation          merge | copy | candidate
```

Исходный manifest остаётся неизменяемым. `derived_from_version` добавляется
аддитивно в `schema_version: 1`: действующие читатели обязаны игнорировать
неизвестные необязательные поля, поэтому исправление не зависит от будущего
blob/manifest-контракта сегмента 2.2. Переход к обязательному `blob_id` повышает
manifest до `schema_version: 2` и выполняется отдельно. Тест, ожидающий отсутствие
manifest в target `v002`, заменяется тестом нового manifest и lineage.

Отдельный read-only аудит находит уже существующие версии без manifest.
Исправление допустимо только при однозначно восстанавливаемом составе и
происхождении; хэши пересчитываются по фактическим файлам, а основание repair
фиксируется. Неоднозначная версия не получает выдуманный lineage: она
помечается `manual_unresolved`, исключается из production-current и получает
владельца решения.

Аудит от 2026-08-07 нашёл 527 manifest на 559 версий, то есть около 32 версий
без manifest. После исправления `register-external` этот исторический набор
должен стать конечным: повторный отчёт обязан показать, что счётчик не растёт.

`project_info.json.pdf_sha256` и `bundle_fingerprint` сейчас участвуют в
legacy-дедупликации. После подключения общего writer главным носителем состава
и per-file SHA-256 является `input_manifest.json`. Поля `project_info.json`
временно остаются проверяемым compatibility-зеркалом: общий writer обновляет их
из тех же рассчитанных значений, а расхождение считается integrity error. Новый
код не выбирает `project_info.json` вместо manifest.

### 6.2. Синтетические документы и тестовые остатки изолируются

До parity всё дерево `projects_v2` инвентаризируется, а каждый документ
попадает ровно в одну категорию:

- production-документ;
- утверждённая синтетическая fixture/галерея;
- тестовый остаток или orphan;
- неразобранный документ, блокирующий cutover.

Известные кандидаты — `GALLERY-*`, которые
`build_vector_graph_gallery.build_document` создаёт прямо в `projects_v2`, и
остаток `214_Obj` с тестовым `legacy_path`. Они не удаляются автоматически:
сначала read-only отчёт, владелец и решение «изолировать / архивировать /
признать production». Любое исключение из parity содержит причину, владельца и
срок устранения.

Генераторы fixtures после исправления получают отдельный явно непроизводственный
root/storage profile. Запись экспериментального скрипта напрямую в
каноническое production-дерево по умолчанию запрещена.

## 7. Порядок переключения

### Фаза A. Обновить baseline и playbook

- назначить владельцев;
- повторно проверить production-флаги;
- актуализировать playbook относительно текущего кода;
- перепроверить открытые блокеры;
- снять число версий без manifest и отдельно найти созданные через
  `register-external`;
- снять метрики fallback и ошибок dual-write;
- классифицировать синтетические документы, fixtures, test leftovers и orphan;
- определить период наблюдения и stop conditions.

### Фаза B. Закрыть read/write-разрывы

- перевести source resolution стадий на v2;
- завершить run promotion;
- сделать v2-aware export;
- закрыть prepare/batch/resume;
- создавать target manifest и `derived_from_version` при merge/copy/candidate;
- подключить общий manifest writer к `register-external` и запретить публикацию
  версии без manifest;
- изолировать прямых писателей синтетики от production-root;
- определить destructive-контракт;
- исключить неявный legacy fallback.

### Фаза C. Теневой production-контроль

В `dual_write_shadow` сравниваются:

- документы и версии;
- состав и SHA-256 входа;
- manifest и lineage каждой вновь созданной версии;
- классификация всех исключений из parity;
- current pointers;
- run и `latest`;
- findings и review;
- export;
- prepare/batch/resume.

Необъяснённое отличие блокирует cutover.

### Фаза D. Backup и maintenance gate

- остановить новые задания;
- дождаться завершения running jobs;
- сделать внешний backup legacy, v2 и прикладных реестров;
- проверить чтение backup и процедуру restore;
- зафиксировать точку возврата и ответственного;
- согласовать maintenance-окно.

### Фаза E. Canary cutover

Включаются:

```text
AUDIT_STORAGE_BACKEND=projects_v2
AUDIT_PROJECTS_V2_WRITE_MODE=projects_v2_primary
AUDIT_PROJECTS_V2_READ_DEFAULT_ENABLED=true
```

На canary-наборе проверяются upload, новый документ, новая версия, полный аудит,
resume, batch, prepare, findings, review, comparison и export.

### Фаза F. Production и наблюдение

После canary флаги включаются в production. На протяжении утверждённого периода
наблюдения контролируются ошибки, fallback, drift, время операций и целостность.
Этап не считается завершённым в момент рестарта backend.

### Фаза G. Rollback drill

До снятия гейта production-записи этапа 2 выполняется учебный возврат в
`legacy + dual_write_shadow`, проверяется читаемость данных и повторный переход
в v2-primary. Данные, созданные только в v2 после cutover, не должны молча
исчезать при rollback; процедура обязана описывать их сохранение и сверку.

## 8. Поведение двух хранилищ после cutover

`projects_v2` — каноника. Legacy — временное зеркало для rollback.

```text
успешная запись v2
    → ответ операции может быть успешным
    → legacy-зеркало обновляется отдельно

ошибка записи v2
    → операция не опубликована

ошибка legacy-зеркала
    → v2 не откатывается
    → создаётся диагностируемая задача восстановления зеркала
```

Новый код не имеет права выбирать legacy только потому, что там «что-то есть».
Fallback допускается лишь в явно названном rollback-режиме.

## 9. Атомарность версии и указателей

Cutover должен предоставить Storage Service этапа 2 одну операцию публикации:

1. блокировка документа;
2. сборка полной версии во временном соседнем каталоге;
3. запись входа, нового manifest и lineage, если версия производна от другой;
4. проверка SHA-256;
5. атомарный rename каталога версии;
6. обновление канонического current и проверяемого зеркала;
7. read-after-write через обычный v2 facade.

При сбое указателя полный каталог версии может остаться неактуальным для
repair, но частичный `01_input` не показывается пользователю.

## 10. Критерии завершения

Этап 1б завершён, когда:

1. Назначены владелец cutover, владелец maintenance и владелец rollback.
2. Playbook актуализирован после 2026-08-26 и ссылается на текущий код.
3. Все семь открытых блокеров закрыты тестами и canary-доказательствами.
4. Реестр production read/write-операций заполнен; обходов v2-контракта нет.
5. Каждая версия в дереве `projects_v2`, допущенная к production-read, имеет
   manifest с известным `schema_version`. Новые merge/copy/candidate всегда
   создают target manifest и `derived_from_version`; исторические дыры либо
   восстановлены однозначно, либо изолированы как `manual_unresolved` с
   владельцем.
   `register-external` использует общий manifest writer; счётчик версий без
   manifest после его включения не растёт. Версия без manifest не может стать
   current или быть допущена к production-read.
6. Синтетические документы, fixtures, test leftovers и orphan
   классифицированы. Прямой writer галереи изолирован от production-root, а у
   каждого временного parity-исключения есть владелец и срок.
7. Parity legacy/v2 не содержит необъяснённых critical/error.
8. Current pointers и выбранные `run_id` согласованы для 100% canary.
9. Upload, new version, merge, audit, resume, batch, prepare, comparison и
   export проходят в v2-only harness.
10. Backup создан на внешнем хранилище и проверен тестовым restore.
11. Canary cutover и stop conditions проверены.
12. Production работает в `projects_v2_primary` весь утверждённый период
    наблюдения без скрытого legacy fallback.
13. Ошибка legacy-зеркала не повреждает и не отменяет каноническую v2-запись.
14. Rollback drill выполнен; данные, созданные после cutover, учтены и не
    теряются.
15. Источник истины и фактические production-флаги отражены в документации и
    диагностическом endpoint.

Только после выполнения этих критериев этап 2 может публиковать новые версии и
файловые результаты в production. Наличие внешнего source adapter для этого не
требуется.

## 11. Что не входит

- реализация опциональных HTTPS/S3/push adapters сегмента 2.5;
- blob/manifest schema 2 Storage Service;
- перенос файлов в собственный S3;
- PostgreSQL;
- удаление legacy-дерева;
- окончательное выключение rollback-копии;
- перенос `workers.db`.

## 12. Владельцы и оценка

Календарная оценка появляется после назначения владельца и повторной оценки
семи блокеров. Это не мешает read-only и контрактным работам 2.0–2.2, но
блокирует их production-публикацию.

| Роль | Состояние |
| --- | --- |
| Владелец этапа 1б | не назначен |
| Владелец приложения во время maintenance | не назначен |
| Ответственный за backup/restore | не назначен |
| Ответственный за manifest, parity, canary и изоляцию fixtures | не назначен |
| Дата cutover | не назначена |
| Период наблюдения | не назначен |

Незаполненная строка является блокером.
