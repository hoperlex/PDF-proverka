# ADR. Внешние источники являются опциональными адаптерами ingest

**Статус:** принято.<br>
**Дата:** 2026-08-27.<br>
**Заменяет:** предварительный ADR канала доставки и прежний этап 2
«Надёжная доставка внешних выгрузок».

## 1. Контекст

В приложении нет сетевого импорта из внешнего S3 или портала. Действующие
маршруты — browser upload и импорт из локального пути, доступного backend.
Внешний S3 ранее рассматривался как отдельный обязательный этап между
`projects_v2` и собственным S3.

Такое разделение создаёт плохую зависимость:

- неизвестен владелец внешней системы и контракт доступа;
- не подтверждены endpoint, bucket/prefix, VersionId и стабильность ID;
- неизвестны egress, SLA и сроки;
- код внешнего connector отсутствует;
- реализация отдельного pipeline дублировала бы staging, ZIP-проверки,
  manifests и публикацию версии;
- собственный S3 и PostgreSQL не должны ждать внешней договорённости.

## 2. Решение

1. Самостоятельный этап внешней доставки упраздняется.
2. Прежний этап собственного S3 становится новым этапом 2 и расширяется до
   единого файлового контура и ingest.
3. Browser upload является обязательным source adapter.
4. HTTPS pull, внешний S3 read-only и push-inbox являются опциональными
   adapters сегмента 2.5.
5. Adapter отвечает только за получение точного потока и канонического
   `ProvenanceRecord` из правил этапа 1 §6.5; собственной source-схемы у adapter
   нет.
6. Проверка, классификация, идемпотентность, создание manifest, запись
   собственных blob и публикация версии выполняются общим ingest.
7. Отсутствие любого внешнего adapter не блокирует этапы 2–5.

## 3. Архитектурная граница

```text
source adapter
  resolve(locator)
  stat()
  open_stream()/resume()
  provenance()
        │
        ▼
общий ingest
  limits → staging → unpack → classify → checksum → precheck
        │
        ▼
Storage Service
  immutable blob → input_manifest → publish version
```

Adapter не имеет права:

- создавать каталог версии напрямую;
- писать в основной namespace bucket;
- менять `document_uid`, `version_id` или current pointer;
- обходить precheck и manifest;
- передавать credentials удалённому воркеру;
- становиться источником истины после публикации версии.

## 4. Обязательный маршрут

Browser upload поддерживается на всём протяжении миграции и после неё. Он
переходит на потоковый staging и общий ingest, поэтому остаётся production
fallback для любого внешнего канала.

Локальный административный импорт допустим только из allowlisted root и также
проходит через общий ingest. Название `register-external` не означает сетевую
интеграцию и не должно использоваться как доказательство готовности S3.

## 5. Условия добавления внешнего adapter

Adapter можно включить в план реализации только при одновременном наличии:

1. назначенного владельца со стороны приложения;
2. подтверждённого владельца внешнего источника;
3. точного locator поколения, видимого оператору или доступного через API;
4. согласованной аутентификации, ротации и области доступа;
5. измеренных размеров, P95, egress и лимитов;
6. сильного validator: VersionId либо эквивалентного immutable generation ID;
7. checksum/размера и безопасного resume;
8. тестового source adapter, проходящего общий ingest contract suite;
9. rollback на browser upload;
10. доказанной экономии ручного времени.

Если условия не выполнены, задача остаётся backlog сегмента 2.5 и не получает
календарной зависимости.

## 6. Допустимые adapters

### 6.1. Authenticated HTTPS pull

Предпочтителен, если портал умеет выдать точную генерацию, длину, digest,
validator и Range. Backend не использует пользовательскую cookie как
межсервисный контракт.

### 6.2. Read-only внешний S3

Допустим для центрального backend через временную роль и узкий bucket/prefix.
Нужны VersionId либо доказанная неизменяемость key, secret management, ротация
и учёт egress.

### 6.3. Push-inbox собственного S3

Внешняя сторона пишет только в карантинный входной prefix. Полученный объект
ещё не является внутренним blob. Центральное приложение проверяет его и
создаёт новый immutable key через Storage Service.

## 7. Граница C-07

Удалённые audit-worker не получают постоянные S3 credentials и не зависят от
S3 во время выполнения задания. Центральный backend формирует существующий
защищённый пакет. Возможность доступа центрального backend к S3 фиксируется
отдельным S3 ADR сегмента 2.0.

## 8. Последствия

Положительные:

- собственный storage развивается без ожидания внешней стороны;
- один ingest и один manifest-контракт вместо двух;
- browser upload сразу получает улучшения памяти и безопасности;
- внешний connector становится небольшим заменяемым adapter;
- сквозная нумерация сокращается до пяти этапов.

Ограничения:

- автоматической внешней загрузки не будет, пока не закрыты условия раздела 5;
- внешний каталог, webhook и multi-source routing не входят в основной план;
- ручная операция останется до появления экономически оправданного adapter.

## 9. Отвергнутые варианты

### Отдельный этап внешней доставки

Отклонён из-за неопределённого контракта, дублирования ingest и блокировки
собственного S3.

### Прямой аудит внешнего объекта

Отклонён: исчезновение или изменение внешнего объекта делает run
невоспроизводимым.

### Выдача S3 credentials воркерам

Отклонена действующей границей C-07 и принципом минимальных прав.
