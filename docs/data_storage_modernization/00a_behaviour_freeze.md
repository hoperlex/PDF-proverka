# Этап 0. Закрепление текущего поведения

> Этот этап предшествует всему остальному. Он нужен одинаково и для
> [этапа 1](01_storage_and_identity_rules.md), и для переписывания фронта, и для
> любого решения о частичной переработке. Пока поведение не закреплено,
> «не сломалось» — это мнение, а не факт.

**Статус:** в работе, начат 2026-08-27.

---

## 1. Что закрепляем и что это ловит

Приложение не имеет спецификации, кроме кода и тестов. Значит спецификацией
нужно сделать **наблюдаемое поведение**, зафиксированное на диске и проверяемое
в CI. Это три независимых слоя, у каждого своя цена и свой класс ошибок.

| Слой | Что закрепляет | Какой класс ошибок ловит | Цена |
| --- | --- | --- | --- |
| 1. Контракт HTTP | поверхность API и формы ответов | молчаливый дрейф API, поломка фронта | дни |
| 2. Golden master конвейера | артефакты анализа на фиксированном корпусе | тихие расхождения в findings — главный убийца | недели |
| 3. Метрика качества | precision/acceptance против решений эксперта | ухудшение качества аудита в целом | дни (частично есть) |

Слои не заменяют друг друга. Слой 1 не знает ничего о качестве анализа. Слой 2
не знает, стало ли лучше — только «стало иначе». Слой 3 знает про качество, но
недетерминирован и не годится как gate на отдельную правку.

## 2. Измеренная исходная точка

| Параметр | Значение на 2026-08-27 |
| --- | --- |
| Python в приложении | ~245 000 строк |
| Тесты | 127 168 строк, 5 980 функций, 45 в известном долге |
| Frontend | 38 099 строк (`app.js` — 16 149) |
| Операций HTTP API | 265 (243 пути) |
| **Операций с типизированной схемой ответа** | **0 из 265** |
| Схем в `components.schemas` | 53 (только запросы и модели) |
| Файлов промптов | 152 |
| Порогов/threshold/confidence в коде | 434 |
| Переменных окружения в коде | 160 |
| LLM-транспортов | 2 (CLI `claude`/`codex`, HTTP OpenRouter) |

**Нулевая типизация ответов — определяющий факт этого этапа.** OpenAPI,
снятый с приложения, описывает пути, методы и параметры, но про форму ответа не
говорит ничего: все обработчики возвращают голый `dict`. Поэтому снапшота
OpenAPI недостаточно, и слой 1 обязан включать golden master **фактических**
ответов, а не только схемы.

Данных в dev-checkout нет (1 версия, ноль артефактов анализа, ноль
`audit_trail/`). Корпус живёт в `AUDIT_DATA_DIR`. Отсюда правило: **инструмент
строится здесь, эталон снимается там**, и снапшоты попадают в репозиторий как
артефакты.

## 3. Слой 1. Контракт HTTP API

### 3.1. Снапшот OpenAPI (1а)

`backend.app.main:app.openapi()` даёт детерминированный спек. Он нормализуется
(сортировка ключей, удаление версии приложения и `servers`) и кладётся в
`contracts/http/v1/openapi.snapshot.json` рядом с уже существующими
`contracts/agent_stream/` и `contracts/worker_certificate/` — по тому же
шаблону «снапшот + тест инвариантов».

Ловит: исчезнувший или переименованный путь, сменившийся метод, пропавший
обязательный параметр, изменившееся тело запроса.

Не ловит: ничего про форму ответа.

### 3.2. Golden master форм ответа (1б)

Для каждой операции записывается фактический ответ на реальных данных, из него
выводится **структурная схема**: набор ключей, типы, nullability, для коротких
строковых доменов — множество значений. Схема, а не сам ответ: ответ содержит
конкретные документы и даты, схема — контракт.

```text
GET /api/projects/{project_id}/versions/{version_id}/findings
  → items[]: {id: str, uid: str|null, severity: enum, page: int|null, ...}
  → meta: {total_findings: int, by_severity: {str: int}}
```

Это и есть контракт, против которого пишется новый фронт на Next/React/TS и
которому обязан удовлетворять любой переписанный backend. Без него новый фронт
будет угадывать форму по коду `app.js`.

Ловит: пропавшее поле, сменившийся тип, `null` там, где фронт ждёт значение,
исчезнувшее значение перечисления.

### 3.3. Тест дрейфа (1в)

Снапшот меняется только явной перезаписью (`--record`), и изменение обязано
попасть в диф коммита. Тест в CI падает на незаявленном изменении поверхности.

## 4. Слой 2. Golden master конвейера

### 4.1. Проблема

Конвейер вызывает LLM. Прогон недетерминирован: тот же документ даёт другой
текст, другой порядок и другое число замечаний. Golden master поверх живых
вызовов бессмыслен.

### 4.2. Решение — запись и воспроизведение кассет

Модель закрепить нельзя. **Всё вокруг модели — можно, и именно там живёт риск.**
Сборка промптов из 152 файлов, парсинг ответов, merge/dedup/перенумерация,
434 порога, grounding, гейты critic, верификация норм — это детерминированный
код, который при переписывании поедет молча.

Значит: фиксируем вход (корпус) **и** ответы модели (кассеты), закрепляем всё
остальное.

### 4.3. Шов записи

Два транспорта — два шва:

| Транспорт | Где перехват | Что уже есть |
| --- | --- | --- |
| CLI `claude` / `codex` | подстановка исполняемых файлов в `PATH` | `pipeline/execution/fake_providers.py` — механизм и точный контракт обоих CLI уже воспроизведены |
| OpenRouter | HTTP-клиент `services/llm/llm_runner.py` | шва нет, нужен |

`fake_providers` сегодня отдаёт **синтетическую** полезную нагрузку, выбранную
по содержимому промпта. Работа этапа — добавить рядом режим `replay`, который
вместо синтетики отдаёт записанный настоящий ответ. Механизм подстановки,
разбор `argv` и знание фактического контракта CLI переиспользуются, а не пишутся
заново.

### 4.4. Ключ кассеты

Ключ — `sha256` нормализованного промпта плюс профиль вызова (провайдер, стадия,
целевой файл из промпта). Нормализация обязательна: в промпт попадают абсолютные
пути, `run_id`, даты и имена временных каталогов. Без нормализации кассета не
переиспользуется на втором прогоне.

Промах кассеты в режиме `replay` — **ошибка, а не тихий фолбэк на живую модель**.
Иначе тест начнёт незаметно тратить деньги и терять детерминизм.

### 4.5. Что закрепляется

Все промежуточные артефакты, а не только итог:

```text
02_text_analysis.json      01_blocks_analysis.json
03_findings.json           03_findings_review.json
norm_checks.json           optimization.json
optimization_review.json   blocks/index.json
document_graph.json        pipeline_log.json (нормализованный)
```

Закрепление промежуточных артефактов — принципиально: если поедет только
`03_findings.json`, по одному итоговому файлу не понять, какая из семи стадий
виновата.

### 4.6. Что нормализуется перед сравнением

Волатильное, не несущее смысла: timestamps, `run_id`, `job_id`, `attempt_id`,
абсолютные пути, `duration_ms`, `response_id`, порядок ключей. Всё остальное
сравнивается точно. Список нормализуемых полей — часть контракта, а не
настройка сравнивателя: расширять его можно только явным решением, иначе
golden master постепенно перестанет что-либо ловить.

### 4.7. Корпус

Не весь массив, а фиксированная выборка, покрывающая режимы: разные дисциплины
(AR, EOM, OV, KJ), документ с `_blocks.json` и без, версия с переаудитом,
версия с экспертными решениями, `legacy_partial`, `source_only`, документ с
векторной графикой. Состав корпуса фиксируется списком `document_uid` +
`version_id` и живёт в репозитории; сами файлы — нет.

## 5. Слой 3. Метрика качества

`scripts/eval_harness.py` уже считает precision/acceptance против
`knowledge_base/decisions_log.json` — 6 440 решений эксперта. Работа этапа
минимальна: снять текущее число, зафиксировать его вместе с датой, размером
выборки и разрезами по дисциплинам, и объявить baseline неухудшения.

Честная оговорка самого харнесса сохраняется: recall из `decisions_log` не
вычисляется — там только то, что аудит выдал и эксперт оценил.

## 6. Порядок

| Шаг | Где выполняется | Блокирует |
| --- | --- | --- |
| 1а. Снапшот OpenAPI + тест дрейфа | dev-checkout | ничего |
| 1б. Запись форм ответа | контур с данными | старт нового фронта |
| 2а. Шов `replay` для CLI и OpenRouter | dev-checkout, тест на фикстурах | 2б |
| 2б. Живой прогон корпуса → кассеты | контур с данными, оплачивается один раз | 2в |
| 2в. Golden-прогон из кассет + сравниватель | CI | рефакторинг конвейера |
| 3. Baseline качества | контур с данными | ничего |

Шаги 1а и 2а не требуют ни данных, ни денег и делаются сразу. Шаг 2б — это
единственная платная часть этапа, и платится она один раз.

## 7. Критерии завершения

1. Снапшот OpenAPI в репозитории; тест падает на незаявленном изменении
   поверхности.
2. Для каждой операции API записана структурная схема ответа; операции, для
   которых её снять не удалось, перечислены явно с причиной.
3. Режим `replay` реализован для обоих транспортов; промах кассеты — ошибка.
4. Корпус зафиксирован списком и покрывает перечисленные в §4.7 режимы.
5. Кассеты записаны; повторный прогон из них воспроизводит все артефакты §4.5
   после нормализации §4.6.
6. Golden-прогон включён в CI и укладывается в приемлемое время.
7. Baseline качества снят и зафиксирован с датой и разрезами.
8. Список нормализуемых полей утверждён и не расширяется молча.

## 8. Чего этот этап не ловит

Честно, чтобы не возникло ложного чувства защищённости:

- **смены поведения самой модели.** Кассеты фиксируют прошлые ответы; новая
  версия модели даст другие. Golden master скажет «код тот же», а качество
  может измениться. Это ловит только слой 3 на живом прогоне;
- **ошибок, которые уже есть.** Golden master закрепляет текущее поведение
  вместе с его дефектами. Это его назначение, а не недостаток, но исправление
  бага будет выглядеть как поломка и потребует явной перезаписи снапшота с
  обоснованием в коммите;
- **производительности и стоимости.** Отдельные метрики, здесь не закрепляются;
- **поведения на данных вне корпуса.** Выборка покрывает режимы, а не всё
  разнообразие 184 документов.
