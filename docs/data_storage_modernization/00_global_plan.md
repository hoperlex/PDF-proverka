# План развития хранения и движения данных

**Редакция:** 2026-08-27<br>
**Статус:** согласованная структура программы; прежний самостоятельный этап
внешней доставки упразднён.

Предлагаемые программные принципы, границы нового control plane и порядок
параллельной гибридной миграции собраны в
[ADR Bible](../architecture/ADR_BIBLE.md) и
[общем roadmap](../architecture/HYBRID_REWRITE_ROADMAP.md). После их утверждения
этот документ остаётся capability-планом данных и хранения внутри программы.

## 1. Зачем нужен план

Рабочие документы уже приведены к структуре `projects_v2`, но метаданные,
файлы и производные результаты всё ещё распределены между каталогами, JSON,
локальным диском, отдельными SQLite-контурами и временными внешними ссылками.
Это усложняет повторный аудит, восстановление после сбоя и работу с большими
комплектами.

Целевая модель проста:

| Слой | Ответственность |
| --- | --- |
| PostgreSQL | документы, версии, запуски, статусы, связи, замечания и решения |
| Собственный private S3 | исходные файлы и долговечные файловые результаты |
| Storage/Metadata API | единственный программный путь к данным |
| Локальный диск | staging, рабочая область и восстанавливаемый кэш |
| Внешние источники | только опциональные поставщики входного потока |
| Индексы и представления | ускорение чтения; их можно построить заново |

## 2. Проверенная исходная точка

- production пока использует legacy как авторитетную запись и
  `projects_v2` как shadow;
- ручная загрузка папок и ZIP через браузер работает;
- импорт из «внешней папки» означает локальный путь, доступный серверу;
- сетевого коннектора к внешнему S3, S3 SDK, credentials и соответствующего UI
  в приложении нет;
- поэтому отдельный проект «автоматическая внешняя доставка» не имеет
  подтверждённого контракта, владельца и измеримой даты готовности.

## 3. Решение по прежнему этапу 2

Прежний этап 2 «Надёжная доставка внешних выгрузок» исключён из сквозной
дорожной карты. Он создавал обязательную зависимость от функции, которой нет в
продукте и которая зависит от внешней стороны.

Полезные требования не удаляются: потоковое чтение, staging, безопасная
распаковка, проверка размера и SHA-256, provenance, идемпотентность, точная
адресация поколения и отсутствие credentials у удалённых воркеров перенесены
в общий ingest нового этапа 2.

HTTPS pull, read-only внешний S3 и push-inbox являются необязательными source
adapters сегмента 2.5. Ни один из них не блокирует собственный S3, PostgreSQL
или ручную работу пользователя. Решение зафиксировано в
[ADR внешних источников](ADR_external_sources_are_optional.md).

## 4. Сквозная нумерация

После удаления прежнего этапа 2 действует следующая нумерация:

| Этап | Название | Результат |
| --- | --- | --- |
| 1 | Идентичность и целостность | непрозрачные ID, manifest schema 1, неизменяемые run, самодостаточные решения |
| 2 | Единый файловый контур, собственный S3 и импорт | manifest schema 2 с `blob_id`, S3 — источник файлов, диск — staging/кэш, все источники входят через один ingest |
| 3 | PostgreSQL для метаданных | транзакционные связи и статусы вместо файловой каноники |
| 4 | Индексация и ускорение чтения | быстрые измеренные запросы, views и кэш производных |
| 5 | Отключение наследия | PostgreSQL + S3 остаются единственными источниками истины |

Обозначения `1Б` и `2.0–2.7` являются подэтапами, а не дополнительными
сквозными этапами.

## 5. Этап 1. Идентичность и целостность

Этап дополняет `projects_v2` постоянными `document_uid`, непрозрачным
`finding_uid = fnd_<ULID>`,
стабильными идентификаторами версий и запусков, самодостаточными решениями
эксперта, manifest schema 1 и неизменяемыми результатами завершённого анализа.

Подэтап 1Б переключает каноническую запись с legacy на
`projects_v2_primary`. Это обязательный гейт перед production-записью файлов в
новый storage-контур.

Документы:

- [правила идентичности](01_storage_and_identity_rules.md);
- [план изменений в коде](01_storage_and_identity_code_plan.md);
- [переключение на `projects_v2_primary`](01b_projects_v2_write_cutover.md).

## 6. Этап 2. Единый файловый контур, собственный S3 и импорт

Прежний этап 3 перенумерован в этап 2 и расширен до полного жизненного цикла
байтов. Он не начинается с внешнего S3. Сначала вводится транспортно-независимый
ingest и Storage Service, затем собственный private S3, и только после этого —
необязательные внешние адаптеры.

### 2.0. Безопасность и baseline

- закрыть небезопасный fallback `export/download`;
- проверить production auth/nginx;
- измерить RAM, локальный диск, размеры комплектов, P50/P95 и стоимость;
- утвердить S3 ADR, retention, backup и границу C-07.

### 2.1. Потоковый ingest

- общий staging на диске;
- передача больших файлов как потоков/`Path`, а не `bytes` в RAM;
- единая безопасная распаковка ZIP;
- один классификатор комплекта для браузера и будущих адаптеров.

Детали: [сегмент 2.1](02_01_streaming_ingest.md).

### 2.2. Storage Core

- `blob_id`, checksum и manifests schema 2;
- единые `put`, `open`, `materialize`, `ensure_derived`;
- локальный adapter для безопасного внедрения до S3;
- запрет прямой файловой записи бизнес-кода мимо Storage Service.

### 2.3. Собственный S3 для новых записей

- private bucket и короткоживущие URL;
- shadow-write и проверка байтов после PUT;
- новые загрузки и завершённые run проходят через общий storage-контур;
- удалённые воркеры получают готовый защищённый пакет, но не S3-ключи.

### 2.4. Историческая миграция и S3-primary

- read-only inventory и расчёт пикового диска;
- append-only migration journal;
- идемпотентный backfill;
- parity, shadow-read, canary и обратимый cutover;
- освобождение локального диска только после restore drill.

### 2.5. Source adapters

Обязательный adapter — browser upload. Дополнительно, только при наличии
владельца, контракта и доказанной пользы, подключается один из вариантов:

- authenticated HTTPS pull;
- read-only внешний S3;
- push во входной карантин собственного S3.

Adapter выдаёт поток и provenance общему ingest. Он не публикует версии, не
пишет напрямую в основной bucket и не является источником истины.

### 2.6. Производные данные и производительность

- Range-чтение PDF;
- локальный кэш с блокировкой на `blob_id`;
- фоновая генерация страниц, миниатюр, кропов и exports;
- `fetch + poll` в UI при cold miss;
- retention по измеренной стоимости восстановления.

### 2.7. Эксплуатация

- квоты, метрики, алерты и аудит доступа;
- versioning/retention/backup и disaster recovery;
- очистка orphan и локального кэша;
- документированный rollback для каждого режима.

Полный документ: [этап 2](02_unified_file_storage_and_ingest.md).

## 7. Этап 3. PostgreSQL для метаданных

После стабилизации UID, `blob_id` и manifest-контрактов метаданные переносятся
из JSON и файловых указателей в PostgreSQL. Переход выполняется через Metadata
Service, shadow-write, backfill, semantic parity и canary. `workers.db` не
считается документным хранилищем и не переносится автоматически.

Полный документ: [этап 3](03_postgresql_metadata.md).

## 8. Этап 4. Индексация и ускорение чтения

Индексы создаются под измеренные запросы PostgreSQL: списки документов,
версии, статусы, даты, замечания и решения. Тяжёлые сводки оформляются как
производные views. Страницы и миниатюры отдаются через кэш/CDN только после
измерения P50/P95 и стоимости.

## 9. Этап 5. Отключение наследия

После полного restore drill и периода наблюдения JSON-reader и legacy-пути
отключаются, локальная rollback-replica архивируется, `_system` и временные
зеркала выводятся по реестру потребителей. PostgreSQL остаётся источником
метаданных, S3 — источником файлов; staging, кэш, индексы и представления
признаются воспроизводимыми.

## 10. Целевой пользовательский маршрут

```text
Браузер / локальный админ-импорт / опциональный внешний adapter
        → потоковый ingest и precheck
        → manifest + собственные immutable blobs
        → публикация версии
        → локальный materialize-кэш
        → подготовка и аудит
        → экспертные решения
        → export через контролируемый content API
```

Пользователь не выбирает физический bucket и не видит credentials. Если
внешний adapter отсутствует, маршрут через браузер остаётся полноценным и не
снижает доступность остальных функций.

## 11. Порядок и зависимости

1. Этап 1 и работы 2.0–2.2, ещё не публикующие данные через новый контур,
   могут идти параллельно. Сегменты 2.1 и 2.2 при этом меняют код production-пути,
   но их новая публикация остаётся выключенной до этапа 1Б.
2. Production-запись этапа 2 требует завершённого подэтапа 1Б.
3. Сегмент 2.5 не является гейтом ни для одного последующего этапа.
4. Этап 3 использует утверждённые UID этапа 1 и `blob_id` этапа 2.
5. Этап 4 начинается после появления реальных SQL-профилей.
6. Этап 5 начинается только после полного parity, backup и restore drill.

Каждый cutover использует одну схему: `baseline → shadow → parity → canary →
primary → observation → cleanup`. Массовое удаление до завершения этой цепочки
запрещено.
