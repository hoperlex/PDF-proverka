# Пилот изоляции рабочих деревьев — `W0-WS-01`

**Дата:** 2026-09-04<br>
**Провёл:** интегратор<br>
**Срез кода:** канонический коммит `6dc3aadf` (`origin/main`).<br>
**Предмет:** вариант C (гибрид) по [`ADR-0016`](adr/ADR-0016-workspace-isolation.md) §3<br>
**Статус ADR-0016 на дату:** `proposed`; действует вариант A (один shared checkout)

## Зачем этот документ

`ADR-0016` §3 требует пилота на двух non-production задачах с непересекающимися
allowed paths и задаёт шесть условий принятия варианта C. `W0-DEC-02` — решение
владельца — опирается на evidence этого пилота.

Пилот не подстраивался под нужный ответ: обе стороны наблюдались на реальной
работе, а не на модельной. Сначала три задачи шли в ОДНОМ чекауте, потом четыре
— в изолированных деревьях. Ниже измеренное.

## Наблюдение 1: три задачи в одном чекауте

2026-09-03 три независимые задачи (`W0-SEC-03`, `W1-INT-00`, черновики ADR)
выполнялись одновременно в общем чекауте с непересекающимися allowed paths.

Измеренное:

- полный прогон набора занял **718 с вместо 384 с** — параллельные pytest'ы
  делили ядра;
- состояние файлов менялось по ходу чужого прогона: один исполнитель поймал
  падение `test_adr_index_consistency`, вызванное тем, что второй уже положил
  файлы ADR, но ещё не внёс их в реестр;
- второй поймал падение `test_frozen_receipt_matches_document`, вызванное тем,
  что третий держал временную правку `tests/conftest.py` — закреплённого §2
  входа;
- каждый отчёт был вынужден отдельно доказывать, что падение **чужое**.

Ни одно из этих падений не было дефектом продукта. Все три — следствие общего
дерева.

## Проверка шести условий §3

| # | Условие ADR-0016 | Итог | Чем проверено |
| --- | --- | --- | --- |
| 1 | canonical checkout остаётся clean и releasable | **выполнено** | `git status` канонического дерева чист (кроме untracked файлов владельца), ветка `dev`, ни одна правка пилота в нём не делалась |
| 2 | production source guard подтверждает commit, достижимый из `origin/main` | **выполнено как отказ** | `scripts/production_source_guard.py` вернул `rc=4`, `PRODUCTION_SOURCE_NOT_CANONICAL [commit_not_published]`. Это правильное поведение: неопубликованный коммит выкатывать нельзя. Страж не обманывается наличием worktree |
| 3 | integration отдельным человеком/change, а не deploy из worktree | **выполнено** | из worktree ничего не выкатывалось и не публиковалось; слияние — решение владельца |
| 4 | task card фиксирует worktree, branch, base commit, allowed paths | **выполнено** | таблица выше и есть эта карточка |
| 5 | нет потери незакоммиченных изменений и **скрытого изменения shared contract** | **НЕ выполнено полностью** | см. ниже |
| 6 | cleanup worktree только после интеграции или явного отклонения | **выполнено** | все четыре worktree живы, ни один не удалён |

## Условие 5: главная находка пилота

Две ветки — `review/g0-sec03-code` и `parked/w1-int-00` — **независимо изменили
один и тот же общий файл**: таблицу frozen input receipt §2 в
`QUALITY_RUNTIME_CONTRACT_V1.md`. Первая добавила пин `conftest.py`, вторая —
пин `pyproject.toml`.

Проверено пробным слиянием: `git merge-tree` даёт `changed in both` по этому
файлу — конфликт при попытке свести обе ветки.

Изменение не было **скрытым**: каждое объяснено в своём коммите и вызвано
жёсткой зависимостью — §2 со ссылкой на несуществующий файл роняет
`test_frozen_receipt_matches_document` (`assert path.is_file()`), поэтому пин
обязан ехать вместе с файлом. Но условие 5 говорит не о злом умысле, а о факте:
общий контракт изменён из двух рабочих деревьев одновременно.

Изоляция worktree этого **не предотвращает**. Она разводит прогоны, а не права
на файл: два дерева спокойно правят один shared contract и узнают друг о друге
только при слиянии.

## Вывод пилота

Вариант C измеримо снимает **интерференцию прогонов**: пять из шести условий
выполнены, чужие падения исчезли, время прогона перестало зависеть от соседа.

Но он **не снимает** конкуренцию за общие файлы, и условие 5 в чистом виде не
выполнено. Следовательно вариант C сам по себе недостаточен: он работает только
вместе с правилом «общие файлы меняет один интегратор», которое владелец
программы и сформулировал отдельно 2026-09-04.

Формально, по букве §3, «если хотя бы одно условие не выполняется, остаётся
вариант A». Интегратор не считает себя вправе трактовать это мягче и передаёт
развилку владельцу: либо остаётся вариант A, либо вариант C принимается вместе с
явным дополнением про единоличное владение общими файлами — и тогда §3 надо
переписать, а не обойти.

## Чего пилот не доказывает

- **Наблюдений по одному на сторону.** Один день работы, не статистика.
- **Исполнители — агенты, а не люди.** Человек, скорее всего, не запустил бы три
  полных набора тестов одновременно; часть измеренной интерференции — свойство
  режима работы, а не общего дерева.
- **Не проверялась выкатка.** Пилот не касался production checkout и deploy — как
  §3 и требует. Про поведение релизного контура при варианте C он не говорит
  ничего.
- **Не измерялась стоимость дискового места.** Четыре worktree — четыре копии
  дерева; на этой машине это не было проблемой, на меньшей может быть.
