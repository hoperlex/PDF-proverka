# ADR-0001. Гибридная миграция по модели Strangler

**Статус:** accepted<br>
**Дата:** 2026-08-27<br>
**Владельцы:** архитектура программы, владельцы backend/frontend/data<br>
**Утверждено:** заказчик, 2026-08-27; выбранный гибридный вариант до запроса ADR Bible<br>
**Supersedes:** нет<br>
**Затронутые принципы:** P-03, P-04, P-10, P-11

## Контекст

Действующее приложение успешно выполняет бизнес-задачу, но файловая каноника,
глобальное состояние, крупные сервисы и монолитный frontend делают полный
рефакторинг опасным. Полностью независимый rewrite потребует заново открыть
неформализованные правила и создаст большой cutover.

## Решение

Новая платформа создаётся рядом с действующей системой и получает владение
вертикальными пользовательскими сценариями по одному. Legacy используется как
behavioral oracle и временный execution engine, но не как архитектурный шаблон.

Порядок каждого перехода:

```text
characterization → contract → shadow → semantic parity → canary
→ primary → observation → legacy consumer removal
```

Первым переписывается control plane: identity, metadata, storage, jobs, API и
frontend. Внутренние stage алгоритмы pipeline переносятся последними и только
по измеримой причине.

## Последствия

Положительные:

- production остаётся работоспособным во время программы;
- ошибки локализуются одним сценарием и имеют rollback;
- PostgreSQL/S3/frontend развиваются параллельно после фиксации контрактов;
- рабочие алгоритмы анализа не переписываются без необходимости.

Отрицательные:

- временно существуют два контура чтения/представления;
- нужны parity harness, reconciliation и строгий реестр владельцев;
- часть команды занята миграцией, а не новой функциональностью.

## Запрещённое толкование

ADR не разрешает создать второй продукт, который месяцами догоняет legacy без
промежуточного production-сценария. Каждая волна обязана завершаться работающим
вертикальным slice и доказательством parity/canary.
