# ADR-0002. Новый control plane начинается модульным монолитом

**Статус:** proposed<br>
**Дата:** 2026-08-27<br>
**Владельцы:** backend architecture<br>
**Утверждено:** не утверждено; решение `W0-DEC-01`<br>
**Supersedes:** нет<br>
**Затронутые принципы:** P-05, P-06, P-07, P-15

## Контекст

Проекту нужны PostgreSQL, S3, durable jobs, новый API и управляемая миграция.
Разделение на microservices до стабилизации bounded contexts увеличит число
сетевых отказов и распределённых транзакций, не устраняя логическую связанность.

## Решение

Новый backend является одним развёртываемым control plane с модулями по bounded
contexts. Модуль публикует application ports и владеет своими таблицами. Прямые
импорты ORM/repository соседнего модуля запрещены.

Допустимые способы связи:

1. синхронный application port внутри процесса;
2. типизированный query/read model;
3. transactional outbox event для асинхронного side effect;
4. anti-corruption adapter к legacy/external системе.

Execution engine и удалённые workers могут оставаться отдельными процессами,
поскольку имеют самостоятельный failure/scaling/security boundary.

## Условие выделения сервиса

Модуль выносится в отдельный сервис только при подтверждённом хотя бы одном
факторе:

- независимое масштабирование даёт измеримый эффект;
- нужен отдельный security boundary;
- отказ модуля должен быть изолирован процессом;
- нужен независимый release cadence;
- runtime/dependency несовместимы с control plane.

Решение о выделении требует нового ADR.

## Последствия

- локальные транзакции остаются простыми;
- разработка и тесты дешевле, чем у ранних microservices;
- модульные границы должны проверяться CI, иначе монолит снова станет связанным;
- composition root является общим hotspot и имеет одного владельца в волне.
