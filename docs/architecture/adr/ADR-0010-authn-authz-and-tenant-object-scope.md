# ADR-0010. AuthN/AuthZ, роли и область объекта нового контура

**Статус:** proposed<br>
**Дата:** 2026-09-03<br>
**Владельцы:** lane API — сессия, роли и проверки в командах; lane OPS — provisioning, ротация, аудит<br>
**Утверждено:** не утверждено<br>
**Decision deadline:** `W0-ADR-06`, review-batch `CB-W0-02`; до старта `W1-API-01` и первого write API нового контура<br>
**Supersedes:** нет<br>
**Superseded by:** нет<br>
**Связанные task IDs:** W0-ADR-06, W0-SEC-01, W0-SEC-03, W0-SEC-04, W1-API-01, W1-WEB-01, W1-WEB-04, W2-INT-03<br>
**Затронутые принципы Bible:** P-01, P-04, P-06, P-10, P-13, P-14

## 1. Контекст

Реестр ADR называет это решение блокирующим для нового write API и нового
маршрута Next. Принцип P-14 требует, чтобы авторизация проверялась на сервере
**для каждого объекта**, а неизвестное состояние auth означало отказ. В
действующем контуре первая половина требования не выполнена: аутентификация
есть, авторизации по объекту нет вовсе.

Решение проектирует auth **нового** контура. Действующий портал оно не
переписывает: его судьбу ведут `W0-SEC-03` (включение auth, срок 2026-10-15) и
`W0-SEC-04` (Origin/intent policy, CSP), а исключение EXC-0001 остаётся
активным до их закрытия.

### 1.1. Подтверждённые факты

Проверено 2026-09-03 на ветке `dev`, коммит `370b6ee8`.

**Аутентификация портала — есть, простая и намеренно такая.**

- `backend/app/core/portal_auth.py`: учётные записи в переменной окружения
  `PORTAL_AUTH_USERS` в виде `логин:pbkdf2_sha256-хэш`; БД пользователей нет.
  Защита от перечисления логинов есть: неизвестный логин всё равно
  проверяется против фиктивного хэша.
- **Сессия stateless.** `issue_token()` формирует
  `base64url(json{"u", "exp"}) + "." + base64url(HMAC-SHA256(body, secret))`;
  серверного хранилища сессий нет. Проверка — `hmac.compare_digest`, срок
  `exp`, плюс проверка, что пользователь всё ещё присутствует в
  `PORTAL_AUTH_USERS`.
- Секрет подписи — `PORTAL_SESSION_SECRET`; если он не задан, генерируется
  эфемерный на процесс, то есть все сессии слетают при рестарте.
  TTL — `PORTAL_SESSION_TTL_HOURS`, по умолчанию 24 часа. Cookie:
  `HttpOnly`, `SameSite=Lax`, `Secure` по схеме или `X-Forwarded-Proto`.
- `PortalAuthMiddleware` работает deny-by-default. Открыты: `/login`,
  `/api/auth/login`, `/api/auth/logout`, `/api/auth/me`, `/api/info`,
  `/favicon.ico` и префикс `/api/v1/worker/`. `/static/**`, `/docs`,
  `/openapi.json` закрыты — это подтверждено тестами.
- WebSocket проверяется отдельно в обработчике (`main.py`), при отсутствии
  сессии соединение закрывается кодом 1008.
- `PORTAL_AUTH_ENABLED` по умолчанию **`false`** — это и есть активное
  исключение EXC-0001.

**Авторизация — существует ровно одна ролевая модель, и не для портала.**

- `backend/app/services/distributed_workers/authorization.py`: права
  `distributed_workers.view`, `.operate`, `.admin`; роли `viewer ⊂ operator ⊂
  admin`; состав ролей — списки логинов в переменных окружения
  `DISTRIBUTED_WORKERS_{VIEWER,OPERATOR,ADMIN}_SUBJECTS`; шаблоны и `*`
  запрещены. Актор берётся **только** из подписанной cookie, а
  `request.state.portal_user` считается подсказкой, а не доказательством.
  Поведение fail-closed: 404 при выключенной подсистеме, 503 при выключенной
  portal auth или битой конфигурации ролей, 401 и 403 в остальных случаях.
  Отказ пишется в журнал (`kind="worker"`, `event="permission_denied"`).
- Второй, несвязанный гейт: `backend/app/api/routers/schedule.py` —
  `_require_admin()` читает `role == "admin"` из `users.json`; при выключенной
  portal auth `PUT /api/schedule/plan` разрешён всем.
- `users.json` — справочник сотрудников (`user_service.py`), а не хранилище
  учётных данных. При этом роутер `/api/users` выполняет CRUD **без единой
  проверки прав**: любой вошедший может изменить `role` сотрудника на `admin`
  и тем самым получить доступ к единственной ручке, которая эту роль читает.

**Проверок владения объектом нет.** Ни один эндпоинт проектов, замечаний,
обсуждений, базы знаний и экспорта не сверяет субъекта сессии с объектом.
Единственное «скоупирование» — `backend/app/core/current_object.py`: middleware
читает **клиентский** заголовок `X-Object-Id` (или query `object_id`) и
привязывает его к контекстной переменной; в его же docstring записано, что
поведение fail-soft и неизвестный `object_id` просто не привязывается. Это
разделение рабочих папок в интерфейсе, а не граница безопасности.

**Понятий tenant и organization в коде нет.** Слова встречаются как поле
штампа чертежа, как атрибут X.509-профиля и как эвристика разбора текста.

**Служебная идентичность — проработана и отделена от портальной.**

- HTTP-контур воркеров: токены с префиксами `wtk_`, `etk_`, `clm_`, на центре
  хранится только sha256, сравнение `hmac.compare_digest`;
  `require_worker()` дополнительно сверяет `X-Worker-Id`,
  `X-Protocol-Version` (426 при несовпадении) и статус регистрации. Три ручки
  открыты намеренно: `POST /register`, `POST
  /identity-reenrollment/complete`, `POST /claim`; на регистрацию действует
  единственный в проекте rate limiter.
- gRPC-контур: mTLS с проверкой SAN сертификата воркера
  (`backend/app/agent_gateway/auth.py`); в `environment == "production"`
  допустим только режим `mtls`. Собственный выпуск сертификатов —
  `backend/app/security/**` и контракт `contracts/worker_certificate/v1`.
- Оба контура намеренно не смешиваются с портальной сессией — это записано в
  комментариях обоих модулей.

**Аудит действий частично есть:** журнал действий пишет `actor` (логин из
cookie); `worker_admin_actions` — append-only с `actor_role`, `permission`,
`source_ip`, `user_agent`, `request_id` и `idempotency_key`; журнал экспертных
решений хранит `expert_reviewer` и `decided_at`.

**Next.js в репозитории отсутствует.** Нет `next.config.*`, нет ни одного
`.tsx`, нет зависимости `next` в `frontend/package.json`. Действующий
интерфейс — многостраничный статик с Vue 3 из глобального бандла; сессия в
браузере нигде не хранится, только httpOnly-cookie, а `portal_auth.js`
оборачивает `fetch` и на 401 уводит на `/login`.

**Контракт не описывает auth.** В снимке
`contracts/http/v1/openapi.snapshot.json` — 243 пути и **нет**
`components.securitySchemes` и `security`.

### 1.2. Чего мы не знаем

- **Кто пользователи и какие роли нужны продукту.** Сегодня это 3–4
  сотрудника с одинаковыми правами. Нужны ли роли «эксперт», «проверяющий»,
  «наблюдатель», «администратор» и чем они различаются в бизнес-смысле —
  **вопрос владельца**, а не архитектуры.
- **Является ли продукт многоарендным.** «Объект строительства» — это
  единица предметной области, а не арендатор. Будут ли внешние организации
  видеть только свои объекты — продуктовое решение с последствиями для схемы
  и для всех запросов.
- Внешний провайдер идентичности (корпоративный SSO) — есть ли он вообще и
  разрешено ли им пользоваться.
- Подтверждённый список сотрудников и защищённый канал выдачи учётных данных
  — вход `W0-SEC-03`, без которого включение auth блокировано.

## 2. Forces и требования

Обязательные свойства:

- авторизация проверяется на сервере для **каждого объекта**; неизвестное
  состояние auth означает отказ (P-14);
- проверка живёт в слое команд/запросов приложения, а не в роутере: роутер не
  является местом бизнес-правила (Bible §5.1);
- решение об отказе имеет стабильный `error_code` и correlation ID; сообщение
  безопасно (domain contract v1 §5);
- каждое изменение состояния несёт актора; отказ авторизации — событие
  durable audit, а не диагностический лог (P-13);
- секреты не попадают в manifest, логи, browser state и job package;
- служебная идентичность (воркеры) и пользовательская сессия остаются
  разными механизмами.

Ограничения совместимости:

- действующий портал не переписывается этим ADR; изменение его auth —
  предмет `W0-SEC-03`/`W0-SEC-04` и расходует отдельный runbook;
- контуры воркеров (`wtk_`/`etk_`/`clm_`, mTLS) остаются как есть: они
  обслуживают работающие удалённые машины;
- пока Next-приложения не существует, «новый route» — это будущий маршрут
  `W1-WEB-04` за route gate ADR-0017.

Срок и команда: одна задача `W0-ADR-06` в review-batch `CB-W0-02` вместе с
ADR-0011.

Намеренно не оптимизируется: самостоятельная регистрация пользователей,
восстановление пароля, делегирование прав, тонкие ACL на отдельное замечание.

## 3. Рассмотренные варианты

### Вариант A. Расширить действующую модель: подписанная cookie + роли в окружении

Новый контур переиспользует `portal_auth`, а роли задаёт списками логинов в
переменных окружения — ровно как это уже сделано для подсистемы воркеров.

Преимущества: ноль новой инфраструктуры; модель уже написана, протестирована
(24 теста) и работает fail-closed; изменение прав не требует релиза БД.

Недостатки: stateless-токен нельзя отозвать — выход не инвалидирует сессию, и
украденная cookie живёт до `exp`; список пользователей в окружении не
масштабируется дальше десятка и не даёт истории «кому что выдали»;
объектная область прав в переменную окружения не помещается в принципе.

Стоимость: минимальная.

Риски: невозможность выполнить P-14 в части объектных проверок — то есть
вариант не закрывает главное требование.

### Вариант B. Серверная сессия и RBAC с объектной областью в БД нового контура

Пользователи, роли и выданные права хранятся в PostgreSQL нового контура;
cookie несёт непрозрачный идентификатор сессии; проверка прав выполняется в
слое команд и обязательно включает проверку принадлежности объекта.

Преимущества: отзыв сессии и «выйти на всех устройствах» становятся
возможными; появляется история выдачи прав; объектная область выражается
данными, а не конфигурацией; проверка попадает в тесты домена, а не в
роутеры.

Недостатки: зависимость от ADR-0007 (без БД вариант нереализуем); каждая
проверка — обращение к БД или к кэшу с инвалидацией; больше кода и больше
миграций; требует продуктового ответа про роли и многоарендность.

Стоимость: одна задача волны 1 и участие в схеме.

Риски: без ответа владельца про роли легко спроектировать модель, которую
потом придётся ломать.

### Вариант C. Внешний провайдер идентичности (OIDC/SSO)

Аутентификация делегируется корпоративному провайдеру; приложение хранит
только права.

Преимущества: пароли и MFA перестают быть заботой приложения; централизованный
отзыв доступа; соответствие корпоративным требованиям, если они есть.

Недостатки: провайдера в контуре сегодня нет; появляется внешняя зависимость,
без которой вход невозможен; для 3–4 сотрудников выгода неочевидна;
локальная разработка требует заглушки.

Стоимость: интеграция плюс административная работа на стороне провайдера.

Риски: решение зависит от наличия провайдера и от политики организации —
это **не архитектурный, а организационный вход**.

## 4. Предлагаемое решение

Решение не принято: статус `proposed`.

### 4.1. Рекомендация

Рекомендуется **вариант B** для нового контура, с сохранением действующей
портальной аутентификации в legacy до завершения переноса маршрутов, и с
**вариантом C как последующим шагом**, если владелец подтвердит наличие
корпоративного провайдера. Форма проверки прав копируется с уже работающей
модели подсистемы воркеров: закрытый список прав, роли как наборы прав,
fail-closed с различением «выключено», «не настроено», «не аутентифицирован»
и «запрещено».

Обоснование:

1. вариант A не может закрыть требование, ради которого ADR существует:
   объектную проверку в переменную окружения не положить;
2. вариант C нельзя рекомендовать первым шагом, потому что наличие провайдера
   не подтверждено; проектировать вход, зависящий от несуществующей системы,
   значит выдумать факт;
3. вариант B оставляет дорогу к C: если провайдер появится, меняется способ
   аутентификации, а модель прав и объектных проверок остаётся;
4. копирование модели прав из `authorization.py` — не экономия, а
   воспроизведение единственной части системы, где fail-closed уже работает и
   покрыт отказами с машинными кодами.

### 4.2. Что фиксируется

**Сессия.**

| Свойство | Решение | Как проверить |
| --- | --- | --- |
| Носитель | непрозрачный `session_id` в cookie; состояние сессии — в БД нового контура | тест: cookie не содержит имени пользователя и не разбирается клиентом |
| Атрибуты cookie | `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/` | тест атрибутов ответа |
| Срок | абсолютный срок жизни сессии и отдельный срок бездействия; оба — параметры конфигурации, значения назначает владелец | старт: 12 часов бездействия и 7 суток абсолютно (предложение, не измерение) |
| Отзыв | выход инвалидирует сессию на сервере; есть операция «завершить все сессии пользователя» | тест: после выхода прежняя cookie отклоняется |
| Секрет/ключи | отсутствие настроенного секрета или хранилища сессий — **отказ старта**, а не эфемерная генерация | тест старта с пустой конфигурацией |
| Неизвестное состояние | отказ (P-14) | тест: битая cookie даёт 401, а не анонимный доступ |

**Роли и права.** Закрытый список прав; роль — именованный набор прав;
пользователь получает роли, а не отдельные права. Стартовый набор —
**предложение, требующее подтверждения владельцем**:

| Роль | Смысл | Может |
| --- | --- | --- |
| `viewer` | наблюдатель | читать объекты, документы, версии, замечания в своей области |
| `expert` | эксперт-проверяющий | всё вышеперечисленное плюс запускать анализ и выносить решения по замечаниям |
| `operator` | эксплуатация | управлять заданиями и воркерами, видеть журналы |
| `admin` | администратор | управлять пользователями, ролями и выдачей области |

Права наследуются по включению, как в действующей модели воркеров.
Соответствие ролей и прав живёт в одном месте и покрыто тестом.

**Область объекта (object scope) — центральное требование.**

- областью выдачи является **объект строительства** (`object_id`), потому что
  это единственная существующая в предметной области единица, которой
  осмысленно ограничить доступ. Более мелкая гранулярность (документ,
  замечание) в v1 не вводится;
- доступ выводится сервером из выданных пользователю областей.
  Клиентский заголовок `X-Object-Id` **перестаёт быть источником области**: в
  новом контуре он допустим только как подсказка выбора, и запрос к
  недоступному объекту даёт отказ, а не пустой результат;
- проверка выполняется в слое команд/запросов: команда получает субъекта и
  идентификатор целевой сущности и обязана доказать доступ через порт
  `AccessPolicy`. Роутер прав не проверяет;
- любая сущность второго уровня (документ, версия, запуск, замечание,
  решение) проверяется **через свой объект**, а не отдельным правилом — иначе
  добавление новой сущности молча создаст дыру;
- запрос, не назвавший объект и не выводимый из целевой сущности, отклоняется:
  «неизвестная область» — это отказ, а не «все объекты».

**Многоарендность.** В v1 не вводится. Объектная область покрывает
наблюдаемую потребность; введение арендатора меняет ключи всех таблиц и
требует продуктового решения. Развилка вынесена в §4.4.

**Служебная идентичность.** Сохраняется разделение трёх контуров:
пользовательская сессия, токены воркеров (`wtk_`/`etk_`/`clm_`), mTLS шлюза.
Новый контур добавляет **четвёртый** случай — внутренние фоновые процессы
(dispatcher outbox, projector, миграции): им выдаётся не пользовательская
сессия, а служебная роль, и в поле актора пишется её идентификатор, как это
уже предусмотрено domain contract v1 §4.6 («`actor` содержит `user_id`
человека либо идентификатор служебной роли»).

**Аудит.**

- каждое изменение состояния несёт актора; отказ авторизации, вход, выход,
  выдача и отзыв роли или области — события **durable audit** с фиксированной
  схемой (потеря записи — инцидент), а не диагностические логи;
- в durable audit пишутся `actor`, право, целевой объект и результат;
  полезная нагрузка запроса и текст исключения — только в диагностику по
  контракту `W0-LOG-01`;
- append-only модель `worker_admin_actions` переиспользуется как образец:
  прежнее/запрошенное состояние, причина, `request_id`, `source_ip` с
  пометкой, что `X-Forwarded-For` является заявленным, а не установленным.

**OpenAPI.** Контракт нового API обязан описывать схему безопасности:
`securitySchemes` и `security` присутствуют, и это проверяется тестом. Сегодня
в снимке legacy их нет — новый контур не имеет права это повторить.

### 4.3. Что решение НЕ делает

- не включает и не выключает auth действующего портала (это `W0-SEC-03`);
- не вводит CSRF-токены и Origin/intent policy для legacy (это `W0-SEC-04`);
- не чинит отсутствие проверки прав на `/api/users` действующего контура —
  это **отдельный дефект безопасности legacy**, который должен получить
  владельца и срок; здесь он только зафиксирован (см. §8);
- не выбирает провайдера идентичности.

### 4.4. Оставшиеся развилки

- **D-1.** Состав ролей и их бизнес-смысл — **решение владельца**. До ответа
  §4.2 остаётся предложением.
- **D-2.** Многоарендность: нужна ли вообще и когда. **Решение владельца**;
  влияет на ключи схемы, поэтому дешевле ответить до `W1-META-02`.
- **D-3.** Внешний провайдер идентичности: есть ли он и разрешён ли.
  **Решение владельца/организации.**
- **D-4.** Сроки жизни сессии и политика бездействия — предложены, требуют
  подтверждения.
- **D-5.** Гранулярность области: только объект или объект + дисциплина.
  Второе выглядит естественным для аудита по разделам, но потребности пока не
  измерены.

## 5. Контракты и данные

- **Source of truth.** Пользователи, роли, выданные области и сессии — модуль
  `access` нового контура (ADR-0006). Портальные учётки legacy остаются в
  окружении до вывода портала из эксплуатации.
- **ID.** `user_id` (`usr_<ULID>`) — уже в реестре domain contract v1;
  `session_id` — непрозрачный, идентичностью пользователя не является и в
  журналы не пишется целиком.
- **Версии.** Схема безопасности описывается в `contracts/api/v1/**`
  (владелец — lane API); изменение набора прав аддитивно, удаление права —
  major.
- **State machine.** Сессия: `active → expired | revoked`; выдача области:
  `granted → revoked` (append-only журнал выдач, действующее состояние —
  проекция, P-12).
- **Consistency.** Выдача и отзыв прав — транзакция с записью события в
  durable audit; кэш прав, если он появится, имеет явную инвалидацию, иначе
  отозванное право продолжает действовать (это отказ fail-closed).
- **Idempotency.** Повторная выдача той же роли на тот же объект не создаёт
  второй записи и не считается ошибкой; отзыв идемпотентен.
- **Retention.** Журнал входов, отказов и выдач прав — по срокам ADR-0014;
  сессии удаляются после истечения.

## 6. Последствия

### Положительные

- `W1-API-01` получает конверт ошибок с кодами авторизации и схему
  безопасности OpenAPI как frozen input;
- P-14 становится выполнимым: у каждой команды появляется обязательная
  объектная проверка;
- отзыв доступа перестаёт быть невозможным: выход и «завершить все сессии»
  работают;
- клиентский `X-Object-Id` перестаёт влиять на видимость данных;
- служебные фоновые процессы получают легальную идентичность вместо
  анонимности.

### Отрицательные и долг

- каждая команда обязана назвать целевую сущность — это дисциплина, которую
  надо удерживать, и первый же забытый вызов создаёт дыру;
- проверка прав добавляет обращение к БД на каждый запрос; без кэша это
  латентность, с кэшем — риск устаревшего права;
- два механизма аутентификации живут параллельно (legacy-портал и новый
  контур) до завершения переноса маршрутов;
- дефекты legacy (отсутствие проверки на `/api/users`, отсутствие rate limit
  на входе, отсутствие отзыва stateless-токена) этим ADR не устраняются и
  остаются открытыми задачами.

### Новые эксплуатационные обязанности

- метрики и алерты: доля 401/403 по маршрутам, всплеск неудачных входов,
  число активных сессий, число отзывов прав. Имена — ADR-0011;
- backup/restore: таблицы пользователей, ролей, выдач и сессий входят в
  резервную копию ADR-0007;
- security rotation/audit: ротация ключей подписи и секретов, периодическая
  ревизия выданных областей, проверка, что отказы попадают в durable audit;
- provisioning: выдача учётных данных по защищённому каналу и подтверждение
  входа — процедура уже описана для `W0-SEC-03` и переиспользуется.

## 7. План внедрения

```text
baseline → contract → shadow → parity → canary → primary → observation → cleanup
```

| Шаг | Владелец | Task ID | Feature mode | Критерий перехода |
| --- | --- | --- | --- | --- |
| baseline | OPS, API | W0-SEC-01 | нет | threat model и карта потоков данных без изменения кода |
| contract | API, OPS | W0-ADR-06 | нет | этот ADR принят; D-1 и D-2 закрыты владельцем |
| shadow | API | W1-API-01 | код на fixtures | `AccessPolicy`, коды ошибок и схема безопасности OpenAPI реализованы без production-трафика |
| parity | API, WEB | W1-WEB-01 | нет | инвентарь маршрутов сопоставлен с требуемыми правами; маршрутов без назначенного права нет |
| canary | WEB, API | W1-WEB-04 | route gate `/next/*` | пилотный маршрут проходит объектную проверку; отказы имеют коды и correlation ID |
| primary | интегратор | W4.3 | cutover по маршрутам | новый контур владеет сессией пользователя |
| observation | OPS | G4 | нет | окно наблюдения без обходов и без ложных отказов |
| cleanup | API, OPS | W5 | нет | портальные учётки в окружении удаляются вместе с legacy-порталом |

Порядок относительно production-изменений W0 сохраняется: `W0-SEC-03`
(включение auth) не выполняется в одну неделю с шагом 4 `W0-OPS-02`, и это
решение его не ускоряет.

## 8. Rollback и failure modes

| Failure mode | Detection | Stop condition | Recovery/Rollback |
| --- | --- | --- | --- |
| Команда не проверила объект | обязательный тест: каждая команда, принимающая идентификатор сущности, вызывает `AccessPolicy` | найдена команда без проверки | сборка красная; команда не выходит в релиз |
| Клиентский `X-Object-Id` расширил видимость | тест: запрос к чужому объекту с подставленным заголовком | любой успешный ответ | область выводится сервером; заголовок остаётся только подсказкой выбора |
| Отозванное право продолжает действовать | тест инвалидации кэша | право действует после отзыва | кэш прав отключается до починки — fail-closed важнее латентности |
| Сессия не отзывается при выходе | тест повторного использования cookie | прежняя cookie принята | серверная сессия обязательна; stateless-режим в новом контуре не допускается |
| Локаут всех пользователей при включении auth | подтверждение входа при provisioning | нет подтверждённого входа хотя бы одного администратора | rollback по runbook `W0-SEC-03`; включение не выполняется без подтверждения |
| Подбор пароля | счётчик неудачных входов | всплеск неудачных попыток | ограничение частоты на вход нового контура; в legacy — открытый дефект, см. ниже |
| Эскалация через `/api/users` (legacy) | ревизия прав | обнаружено изменение роли неадминистратором | **открытый дефект действующего контура**: требует владельца и срока; ADR фиксирует его, но не чинит |
| Отказ авторизации не попал в durable audit | проверка каналов журнала | отказ виден только в диагностике | классификация события исправляется: отказы — durable audit |

## 9. Доказательства принятия

- contract tests: `contracts/api/v1/**` содержит `securitySchemes` и
  `security`; каждый маршрут имеет назначенное право; отказы соответствуют
  каталогу кодов domain contract v1;
- тест обхода: набор запросов к чужому объекту по каждому классу сущностей
  (документ, версия, запуск, замечание, решение, экспорт) обязан получать
  отказ;
- тест жизненного цикла сессии: выдача, истечение, выход, «завершить все
  сессии», битая и подделанная cookie;
- semantic parity: поведение действующего контура не меняется — регресс-гейт
  без новых падений;
- security review: threat model `W0-SEC-01` пройдена по каждому пункту;
  секреты отсутствуют в логах, manifest и job package;
- canary: пилотный маршрут `W1-WEB-04` работает с включённой объектной
  проверкой, доля ложных отказов измерена.

## 11. Критерии пересмотра

- решение пересматривается, если владелец подтвердит многоарендность:
  область объекта окажется недостаточной, и ключи схемы придётся менять до
  `W1-META-02`;
- если появится корпоративный провайдер идентичности — вариант C оформляется
  новым ADR со ссылкой `supersedes` в части аутентификации;
- если доля ложных отказов на canary превысит 1 % запросов, гранулярность
  области (D-5) пересматривается;
- если `W0-SEC-03` не закроет EXC-0001 к 2026-10-15, это стоп-условие
  Gate G0 независимо от статуса этого ADR;
- после перевода первого write API в primary набор прав сверяется с
  фактическим использованием: право, не проверенное ни разу, подозрительно.
