# Domain contract v1: идентификаторы, состояния и ошибки

**Статус:** проект контракта; нормативная сила — после принятия ADR-0018<br>
**Версия контракта:** v1; frozen input волны 1<br>
**Редакция:** 2026-08-28<br>
**Владельцы:** lane ARC — словарь и идентичность; lane API — ошибки<br>
**Связанные task IDs:** W0-ARC-02, W1-META-01, W1-STO-01, W1-API-01<br>
**Машиночитаемая форма:** `contracts/domain/v1/**`

Термины этого документа определены в [глоссарии](GLOSSARY.md). Раскладку и
зоны владения задаёт [ADR-0006](adr/ADR-0006-target-repository-layout.md),
нормативную силу контракту даёт
[ADR-0018](adr/ADR-0018-domain-contract-v1.md).

## 1. Назначение и область

Контракт превращает договорённости об идентичности, состояниях и ошибках в
проверяемую форму, от которой волна 1 стартует параллельно: `W1-META-01`
строит value objects и state machines, `W1-STO-01` — ports хранения,
`W1-API-01` — error envelope и OpenAPI seed.

Область применения — новый контур: `src/auditmanager/**`, `web/**` и
`contracts/api/v1/**`. Действующий контур контракт не меняет: замена
идентификаторов, статусов или формы ответа в legacy является изменением
бизнес-поведения и расходует capability slot, поэтому не выполняется этой
задачей (P-17). Сопоставление двух контуров описано в §6.

Не входит в v1 и решается другими документами:

| Тема | Владелец решения |
| --- | --- |
| durable job/attempt state machine, leases, outbox | ADR-0009, `W0-ADR-03` |
| TTL, retention и erasure workflow | ADR-0014, `W0-ADR-05` |
| роли, object scope и правила доступа | ADR-0010, `W0-ADR-06` |
| физическая схема PostgreSQL и миграции | ADR-0007, `W0-ADR-01` |
| формат input/result package legacy-движка | ADR-0012, `W0-ADR-08` |
| имена метрик, трасс и SLO | ADR-0011, `W0-ADR-07` |
| статусы норм, сравнения и bootstrap воркеров | волны 2–4 |

## 2. Правила именования

- одно понятие имеет одно имя в коде, API, журналах и схеме БД; синоним
  вводится только как явный legacy-алиас из §3.4;
- машинные значения — латиница `snake_case`; человекочитаемые подписи
  живут в отдельных display-полях и не участвуют в сравнении;
- имя поля идентификатора совпадает с именем сущности: `document_uid`,
  `run_id`, `finding_uid`; поле `id` без квалификатора запрещено;
- список запрещённых синонимов канонических имён:

| Канон | Не используется в новом контуре |
| --- | --- |
| `finding` | `discrepancy`, `issue`, `remark`, `item` |
| `finding_uid` | `finding_id`, `F-NNN` как ключ |
| `run_id` | `analysis_run_id`, `job_id` в значении запуска |
| `document_uid` | `project_id` как путь, `document_code` как ключ |
| `version_id` | `logical_version_id`, `physical_version_id` |
| `severity` | `criticality`, `priority` |
| `analysis_status` | `status` без квалификатора |

## 3. Идентификаторы

### 3.1. Общие правила

- идентификатор непрозрачен: не содержит пути, имени, даты, дисциплины и
  порядкового номера, не парсится для восстановления связей (P-01, P-02);
- каноническая форма — `<prefix>_<ULID>`: три-четыре символа префикса,
  подчёркивание и 26 символов Crockford base32 в верхнем регистре;
- идентификатор выдаётся один раз портом `IdGenerator` в
  `src/auditmanager/shared/**`; domain-код не вызывает `uuid4()` напрямую
  (P-06);
- сравнение идентификаторов — побайтное; нормализация регистра, обрезка и
  дополнение запрещены;
- человекочитаемая ссылка (`display_ref`, `F-006`, `v003`) существует
  только как поле отображения и никогда не является ключом или FK;
- неизвестный идентификатор даёт ошибку из §5.3, а не тихий поиск по
  соседним признакам (P-10): для сущности с собственным кодом это
  `*_not_found`, для остальных — `entity_not_found` с полем
  `details.entity`; нарушение формы идентификатора —
  `invalid_identifier_format`;
- формы, отличные от `<prefix>_<ULID>`, заданы явно: `version_id` —
  `^v[0-9]{3,}$`; `pdf_page` — целое не меньше 1; `discipline_code` —
  `^[A-Za-z][A-Za-z0-9_]*$`; роль файла и роль артефакта —
  `^[a-z][a-z0-9_]*$`; `worker_id` — `^wrk_[0-9a-f]{8,32}$`;
  `instance_id` — `^inst_[A-Za-z0-9][A-Za-z0-9._-]{2,122}$`.

`worker_id` и `instance_id` сохраняют действующий формат: их регулярные
выражения зафиксированы в
`backend/app/services/distributed_workers/identity_reenrollment.py:38-39`
и обслуживают работающих удалённых воркеров. Это осознанное отклонение от
формы `<prefix>_<ULID>`, ограниченное двумя полями.

Ещё пять идентификаторов принятый plan contract правил идентичности
оставляет существующими (§5: «существующий `object_id`», `job_id`,
`attempt_id`, `session_id`, `pair_id`). Контракт v1 выдаёт им новую
непрозрачную форму, потому что действующие значения либо не непрозрачны
(`session_id` и `pair_id` — усечённый hex без области уникальности), либо
несут двойной смысл (`job_id`, используемый как `run_id`). Перенос
описан строками §3.4; до завершения переноса читатель обязан принимать обе
формы.

### 3.3. Разрешённые составные ключи

| Ключ | Состав | Почему допустим |
| --- | --- | --- |
| Дисциплина | `object_id` + `discipline_code` | код раздела уникален внутри объекта |
| Версия | `document_uid` + `version_id` | `version_id` уникален только внутри документа |
| Страница | `document_uid` + `version_id` + `pdf_page` | страница не является сущностью с собственной жизнью |
| Входной файл | `document_uid` + `version_id` + роль файла | роль берётся из закрытого реестра; `blob_id` адресует байты, но ключом версии не является |
| Артефакт | `run_id` + роль | роль берётся из закрытого реестра ролей |
| Блок | `document_uid` + `version_id` + поколение источника + `block_id` | `block_id` без этого контекста ссылкой не является |
| Пара сравнения | `session_id` + `pair_id` | пара уникальна внутри сессии |
| Решение по замечанию | `finding_uid` + `decision_id` | замечание неизменяемо, решений может быть несколько |

Порядковый номер версии используется для отображения и сортировки.
Определять актуальную версию разбором максимума `vNNN` запрещено:
актуальность хранится указателем `current_version_id` с одним владельцем.

### 3.4. Legacy-алиасы

Алиас читается новым контуром через adapter, не создаёт второго имени в
новых контрактах и удаляется вместе с legacy-потребителем.

| Алиас действующего контура | Канон v1 | Режим |
| --- | --- | --- |
| `project_id` как путь `<дисциплина>/<папка>` | `object_id` + `discipline_code` + `document_uid` | чтение через adapter, отображение в mapping-таблице `W0-DATA-02` |
| `analysis_run_id` в `version.json` | `run_id` | только чтение |
| `run_id`, равный `job_id` живого аудита | раздельные `run_id` и `job_id` | не переносится: разбирается миграцией |
| `F-NNN`, `T-NNN`, `G-NNN`, `OPT-NNN` | `finding_uid` + `display_ref` | номер сохраняется как display-поле |
| `DEC-NNNN` | `decision_id` | только чтение |
| `blk_<32hex>` и `A64J-JJPV-A7Y` | `block_id` | оба поколения сохраняются в mapping, новые блоки — `blk_<ULID>` |
| `logical_version_id`, `physical_version_id` | `version_id` | только чтение |
| существующие `object_id`, `job_id`, `attempt_id` | `obj_<ULID>`, `job_<ULID>`, `att_<ULID>` | mapping, обе формы принимаются до конца переноса |
| существующие `session_id`, `pair_id` (усечённый hex) | `ses_<ULID>`, `par_<ULID>` | mapping, обе формы принимаются до конца переноса |
| `ordinal` действующего отчёта | `ordinal` сохраняется, ключом не является | только чтение |
| `current_version.txt`, `document.json.current_version` | `current_version_id` | только чтение |

## 4. Состояния

### 4.1. Общие правила

- состояние хранится одним полем с закрытым списком значений; набор
  булевых флагов состояние не заменяет (P-09);
- у каждой машины один владелец записи и один модуль, где определены
  переходы; переход выполняется в транзакции вместе с записью события;
- инициатор из таблицы переходов запрашивает переход, а запись поля
  выполняет владелец машины: второй авторитетный писатель запрещён;
- переход вне таблицы отклоняется ошибкой `state_transition_not_allowed`;
- неизвестное значение состояния при чтении отклоняется явно и не
  подменяется значением по умолчанию (P-10);
- терминальное состояние не покидается; исправление создаёт новую
  сущность — версию, запуск или редакцию (P-03).

### 4.2. Версия документа: `analysis_status`

Владелец записи — `documents`.

| Значение | Смысл | Начальное | Терминальное |
| --- | --- | --- | --- |
| `none` | версия принята, анализ не выполнялся | да | нет |
| `partial` | есть завершённый запуск с неполным набором артефактов | нет | нет |
| `complete` | есть завершённый запуск с полным набором артефактов | нет | нет |
| `legacy_partial` | состояние импортировано из действующего контура | нет | нет |
| `source_only` | загружен только источник, анализ не переносился | нет | нет |

| Из | В | Инициатор | Условие |
| --- | --- | --- | --- |
| `none` | `partial` | jobs | запуск завершён с неполным набором артефактов |
| `none` | `complete` | jobs | запуск завершён с полным набором артефактов |
| `partial` | `complete` | jobs | новый запуск дал полный набор артефактов |
| `complete` | `partial` | jobs | новый актуальный запуск неполон |
| — | `legacy_partial` | migration | импорт версии с неполным анализом |
| — | `source_only` | migration | импорт версии без анализа |
| `legacy_partial` | `partial` | jobs | новый запуск завершён с неполным набором артефактов |
| `legacy_partial` | `complete` | jobs | новый запуск завершён с полным набором артефактов |
| `source_only` | `partial` | jobs | новый запуск завершён с неполным набором артефактов |
| `source_only` | `complete` | jobs | новый запуск завершён с полным набором артефактов |

Значения `legacy_partial` и `source_only` присваивает только миграция:
они существуют, чтобы импортированная версия не выглядела как результат
нового анализа. Терминальными они не являются — версия действующего
контура может быть переанализирована в новом и тогда получает `partial`
или `complete`. Новая цепочка вида `draft → ready → processing` для
версии не вводится.

### 4.3. Запуск анализа: `run_state`

Владелец записи — `jobs`.

| Значение | Смысл | Начальное | Терминальное |
| --- | --- | --- | --- |
| `running` | запуск создан и выполняется | да | нет |
| `complete` | результат опубликован и проверен | нет | да |
| `failed` | запуск завершён без публикуемого результата | нет | да |
| `cancelled` | запуск остановлен по команде | нет | да |

| Из | В | Инициатор | Условие |
| --- | --- | --- | --- |
| `running` | `complete` | jobs | манифест запуска записан с известным `schema_version`, checksum сверены |
| `running` | `failed` | jobs | терминальная ошибка исполнения |
| `running` | `cancelled` | operator | принята команда отмены |

Инварианты: актуальным запуском версии становится только `complete`;
манифест запуска содержит целочисленный `schema_version`, и читатель
принимает только известные версии, иначе отвечает
`unsupported_manifest_version`; завершённый запуск неизменяем; повторная
публикация того же результата идемпотентна и не создаёт второй запуск
(P-08).

### 4.4. Импорт входного комплекта: `import_state`

Владелец записи — `ingest`.

| Значение | Смысл | Начальное | Терминальное |
| --- | --- | --- | --- |
| `received` | комплект принят, проверки не выполнены | да | нет |
| `validated` | состав, checksum и дубликаты проверены | нет | нет |
| `published` | версия создана, входные файлы неизменяемы | нет | да |
| `rejected` | комплект отклонён с машинной причиной | нет | да |

| Из | В | Инициатор | Условие |
| --- | --- | --- | --- |
| `received` | `validated` | ingest | пройдены проверки состава и checksum |
| `received` | `rejected` | ingest | `checksum_mismatch`, `input_bundle_incomplete` или `duplicate_input_bundle` |
| `validated` | `published` | ingest | создана версия, зафиксирован `input_manifest` с известным `schema_version` |
| `validated` | `rejected` | operator | отклонение оператором до публикации |

Инвариант: после `published` состав входных файлов версии не меняется;
исправление выполняется новой версией.

### 4.5. Объект хранения: `blob_state`

Владелец записи — `storage`; машина применяется к любому `blob_id`,
включая входные файлы и артефакты запуска.

| Значение | Смысл | Начальное | Терминальное |
| --- | --- | --- | --- |
| `temporary` | загрузка начата, объект не подтверждён | да | нет |
| `verified` | размер и SHA-256 совпали с заявленными | нет | нет |
| `published` | объект доступен читателям и неизменяем | нет | да |
| `abandoned` | загрузка прервана, объект подлежит уборке | нет | да |

| Из | В | Инициатор | Условие |
| --- | --- | --- | --- |
| `temporary` | `verified` | storage | контрольная сумма совпала |
| `temporary` | `abandoned` | storage | таймаут загрузки или явная отмена; обращение к такому объекту даёт `upload_expired` |
| `verified` | `published` | storage | объект связан с версией или запуском |
| `verified` | `abandoned` | storage | связывание не произошло в срок |

### 4.6. Экспертное решение и проекция замечания

Замечание неизменяемо внутри своего запуска и собственного изменяемого
состояния не имеет. Решение эксперта — append-only событие:

| Значение `decision_verdict` | Смысл |
| --- | --- |
| `accepted` | замечание принято экспертом |
| `rejected` | замечание отклонено с обязательной причиной |
| `revoked` | предыдущее решение отозвано автором или владельцем |

Действующим считается последнее решение по `finding_uid`, не отменённое
событием `revoked`. Производная проекция `finding_review_state` принимает
значения `undecided`, `accepted`, `rejected` и перестраивается из журнала
решений (P-12). Перенос решения на новый запуск — не состояние, а связь
`carried_from_decision_id` в новом решении.

Решение самодостаточно: оно остаётся читаемым, даже если исходный запуск
или представление утрачены. Обязательные поля повторяют состав §6.9
принятых правил идентичности:

- `decision_id`, `finding_uid` и `ordinal` замечания на момент решения;
- `document_uid`, `version_id` и `run_id`, из которого взято замечание;
- краткая суть замечания, его категория и `severity`;
- страница, лист и связанные `block_id`;
- нормативные ссылки;
- `decision_verdict`, `actor` и `decided_at`;
- `reason` — обязателен для `rejected` и `revoked`.

Поле `actor` содержит `user_id` человека либо идентификатор служебной
роли; иных значений оно не принимает.

### 4.7. Классификация замечания

`severity` — закрытый список машинных значений; русские формулировки
действующего контура становятся display-подписями.

| Машинное значение | Подпись | Источник в действующем контуре |
| --- | --- | --- |
| `critical` | Критическое | `КРИТИЧЕСКОЕ` |

## 5. Ошибки

### 5.1. Конверт

Единая форма ответа об ошибке нового контура:

```text
{
  "error_code":     "version_not_found",
  "message":        "Версия документа не найдена",
  "retryable":      false,
  "correlation_id": "corr_01J9Z2M0RS3P4T5V6W7X8Y9Z0A",
  "stage":          "documents.get_version",
  "details":        { "document_uid": "doc_01J9Z2M0RS3P4T5V6W7X8Y9Z0B" }
}
```

Правила:

- `error_code` — стабильный машинный код из §5.3; клиент принимает
  решения только по нему;
- `message` — безопасное сообщение для человека: без путей, query,
  presigned URL, cookies, токенов, ПДн и текста исключения (P-13,
  контракт redaction `W0-LOG-01`);
- `retryable` — признак осмысленности повтора; повтор безопасен только
  вместе с idempotency key;
- `correlation_id` присутствует всегда и совпадает с идентификатором в
  журналах и трассах;
- `stage` присутствует всегда и называет операцию или стадию, где ошибка
  возникла: ошибка без диагностируемой стадии и идентификатора сущности
  не считается нормально обработанной (P-13);
- `details` обязателен для кодов, адресующих сущность, и содержит её
  идентификатор; состав полей задаёт allowlist конкретного кода,
  произвольная структура запрещена;
- HTTP-ответ с ошибкой никогда не имеет статуса 2xx: ответ 200 с полем
  `error` в теле запрещён.

### 5.2. Правила кодов

- код стабилен, не переиспользуется под другим смыслом и не удаляется без
  major-версии контракта;
- код в `snake_case`, без идентификаторов сущностей и пользовательского
  ввода внутри значения;
- один код — одна причина; ветвление по тексту сообщения запрещено;
- код, отсутствующий в реестре `contracts/domain/v1/errors.json`, не
  публикуется наружу;
- ошибка отвечает только статусами 400, 401, 403, 404, 409, 413, 422,
  429, 500, 503 и 504; иной статус в каталоге не допускается.

### 5.4. Связь с gRPC-контуром

Поля конверта повторяют `ErrorStatus` из
`contracts/agent_stream/v1/common.proto`: `code`, `safe_message`,
`retryable`, `correlation_id`. Транспорты остаются раздельными; общими
являются семантика полей и требование стабильного кода. Значения
`ErrorCode` protobuf в HTTP-каталог не переносятся и наоборот.

### 5.5. Действующий контур

Действующий контур не имеет единой формы ответа об ошибке. Измерено
2026-08-28 на коммите `b3a56a3c`: 461 вызов `HTTPException` в
`backend/app`, из них 189 передают наружу текст исключения; различных
машинных кодов в поле `error` — 12; встречаются ответы 200 с полем
`error` в теле. Контракт v1 действующий контур не меняет: приведение
выполняет adapter нового контура при переносе маршрута, а
характеризационный тест фиксирует прежнюю форму до cutover.

## 6. Соответствие действующему контуру

| Действующий контур | v1 | Действие миграции |
| --- | --- | --- |
| `project_id` как путь | `object_id`, `discipline_code`, `document_uid` | mapping-таблица `W0-DATA-02`, ambiguity report |
| `F-NNN` как ключ решения | `finding_uid` + `display_ref` | восстановление связи решений по фингерпринту |
| `run_id == job_id` | раздельные `run_id`, `job_id` | принятые правила идентичности §6.7 разрешают совпадение для живого аудита; v1 сужает это разрешение, потому что одно задание может дать несколько запусков; история разбирается при импорте |
| `analysis_status` версии | тот же список значений | значения сохраняются без переименования |
| статусы этапов `pipeline_log.json` | не переносятся в v1 | остаются в действующем контуре |
| `severity` русскими строками | `severity` латиницей + подпись | таблица §4.7 |
| формы ответа об ошибке | конверт §5.1 | приведение на границе маршрута |

## 7. Совместимость и версионирование

- контракт версионируется каталогом `contracts/domain/v1/`; несовместимое
  изменение создаёт `v2` отдельной integration task;
- добавление необязательного поля или нового `error_code` версию не
  повышает; удаление кода, изменение его смысла, сужение списка значений
  состояния и переименование поля — повышает;
- читатель отклоняет неизвестную major-версию явно и принимает неизвестные
  необязательные поля известной версии;
- владелец версии — lane ARC; потребитель не меняет схему в своей задаче
  (ADR-0003).

## 8. Проверки и доказательства

- машиночитаемая форма в `contracts/domain/v1/**` является источником для
  генерации кода и тестов; markdown и JSON расходиться не должны;
- тест `tests/test_domain_contract_v1.py` проверяет: уникальность
  префиксов идентификаторов и их вывод из колонки «Формат»,
  соответствие таблиц markdown и JSON, замкнутость переходов состояний,
  достижимость каждого значения, отсутствие исходов из терминального
  значения и тупиков среди нетерминальных, уникальность `error_code`,
  допустимость HTTP-статусов и совпадение реестра §3.2 с §2.1 глоссария;
- `W1-META-01` подтверждает контракт domain unit-тестами без I/O;
- `W1-API-01` подтверждает конверт contract-тестами и генерацией OpenAPI;
- нарушение формы идентификатора или неизвестное состояние обязаны давать
  типизированную ошибку, а не приведение к значению по умолчанию.

## 9. Открытые развилки

- **F-1.** Формат `worker_id` и `instance_id` сохранён действующим; вопрос
  их приведения к общей форме решается вместе с ADR-0009.
- **F-2.** Реестр ролей артефактов и ролей входных файлов фиксируется
  `W1-STO-01` на основе манифеста; v1 задаёт только требование закрытого
  реестра.
- **F-3.** Состав `details` по каждому коду ошибки фиксирует `W1-API-01`
  вместе с OpenAPI seed.
- **F-4.** Идентификатор блока в новом контуре (`blk_<ULID>`) требует
  решения о судьбе двух действующих поколений — предмет `W0-DATA-02`.
- **F-5.** Принятые правила идентичности §6.4 откладывают `blob_id` до
  появления собственного S3 или PostgreSQL. Контракт вводит его сразу,
  потому что новый контур проектируется с обоими; до первого storage
  adapter значение остаётся неиспользуемым.
