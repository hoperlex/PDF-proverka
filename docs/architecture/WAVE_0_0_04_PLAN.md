# Version-срез 0.0.04 и дорога к CP1

**Статус:** evidence-фаза 1 принята; фиксация version-среза выполняется отдельной
распиской после контрольного прогона. Это не Gate G0 и не разрешение W1-cutover.<br>
**Дата:** 2026-09-04<br>
**База кандидата:** `origin/main@6dc3aadf`<br>
**Следующая контрольная точка:** `CP1` — safe legacy: redaction, auth и watchdog
захвачены в репозиторий.<br>
**Источник критериев:** [roadmap](HYBRID_REWRITE_ROADMAP.md), разделы «Порядок
изменений, затрагивающих production» и «Gate G0»; определение checkpoint —
[checkpoints/README.md](checkpoints/README.md).

## 1. Что именно принято в 0.0.04

Фаза 1 сдала шесть evidence-задач. Приёмка означает, что неизвестные величины
измерены, расхождения названы, а входы для следующих решений воспроизводимы:

| Задача | Принятый результат | Что этим не закрыто |
| --- | --- | --- |
| `W0-BEH-01` | 30 journeys: 16 с детерминированным сквозным тестом, 14 с частичным покрытием | golden fixtures и LLM replay (`W0-BEH-02`, `W0-LLM-02`) |
| `W0-DATA-01` | 55 категорий и 24 развилки с вариантами и ролью решающего | решения по развилкам и числовая retention matrix |
| `W0-OPS-01` | форма из 24 величин, 17 локально измерены | семь production-величин, включая пять обязательных для G0; Task ID остаётся открытым |
| `W0-STD-01` | 51 положение классифицировано; ADR не выдают неподтверждённое за обязательное | подтверждение версии стандарта либо запущенный и истёкший decision timeout; Task ID остаётся открытым |
| `W0-LEG-01` | предел capability slot соблюдён; 11 sustainment-позиций распределены | именованный интегратор, denominator и первый недельный отчёт; Task ID остаётся открытым |
| `W0-LLM-01` | 58 mutable sources; 15 непреодолимых позиций разнесены на четыре класса | ADR-0013, sanitized cassettes и replay |

Пилот `W0-WS-01` входит в пакет как контроль способа интеграции, но не считается
седьмой evidence-задачей фазы 1. Он подтвердил изоляцию рабочих деревьев и
оставил решение о правах на shared-файлы владельцу `W0-DEC-02`.

Version-срез фиксирует **доставку evidence**, а не искусственное закрытие всех
Task ID. По [G0-readiness delta](G0_READINESS_DELTA.md) выполнены только условия
11 и 12; условие 4 частично, шесть условий измерены, но не закрыты, три не
выполнены и два требуют решения других владельцев. Поэтому:

- Gate G0 не пройден;
- массовая реализация W1 не разрешена;
- черновики ADR-0007…ADR-0012 остаются `proposed` до индивидуальной приёмки;
- локальная проверка кандидата не подменяет CI опубликованного commit.

## 2. Граница фиксации версии

Версия `0.0.04` считается зафиксированной локально, когда:

1. минимальные исправления согласованности, этот план, тест целостности
   архитектурного комплекта и копия обязательных эталонов stage-comparison в
   `tests/fixtures/**` входят в границу `6dc3aadf..772f8523`; кандидат не
   docs-only, и его граница объявлена не памятью автора, а
   [распиской границы](receipts/0.0.04-candidate-boundary.json),
   проверяемой командой `git diff --shortstat`;
2. JSON-расписки валидны, относительные ссылки разрешаются, document-contract
   tests и regression gate зелёные;
3. отдельная расписка `receipts/0.0.04-phase1.json` называет проверенный source
   commit, команды и фактические результаты;
4. неизменяемая локальная ветка `version/0.0.04` указывает на commit с этой
   распиской.

Публикация — отдельный этап. До push review-ветки, зелёного GitHub CI и merge в
актуальный `origin/main` срез не называется опубликованным release. Remote-ветка
`version/0.0.04` создаётся только от достижимого из `origin/main` commit и после
отдельной проверки, что имя ещё свободно.

## 3. Критический путь к CP1

CP1 — checkpoint, а не gate: он обязан честно захватить состояние safe legacy,
но сам по себе не разрешает следующий cutover. Критический путь не расширяется
задачами, которые нужны для G0, но не входят в определение CP1.

```text
P0 публикация 0.0.04 в origin/main
 ├─ L1 redaction: контракт → тесты → готовность rollout ── L2 rollout
 ├─ S1 auth: код/review + provisioning + rollback ─────── S2 rollout
 ├─ O1 watchdog: снимок → endpoints → shadow ──────────── O2 cutover
 └─ E1 шаблон evidence/rollback ───────────────────────── E2 CP1 receipt

production-порядок: L2 → S2 → отдельная неделя → O2 → E2
```

### P0 — публикационная база, последовательно

1. Опубликовать review-кандидат `0.0.04`, дождаться зелёного GitHub CI и
   проверить source SHA артефактов.
2. Свести только проверенный SHA в актуальный `origin/main`.
3. Повторно проверить CI на merge commit, выпустить release receipt и только
   затем создать remote `version/0.0.04`.
4. Перенести существующий кандидат кода `W0-SEC-03` на новую базу через
   отдельное review; наличие кода не выдавать за выполненный production rollout.

Stop condition: divergence с `origin/main`, красный/отменённый CI, неполный
JUnit или несовпадающий source SHA запрещают merge. По обязательной политике
[acceptance-rework/v1](ACCEPTANCE_REWORK_POLICY_V1.md) после первой
неуспешной попытки разрешён только один классифицированный remediation commit
внутри frozen scope и один финальный прогон. Второй неуспешный прогон завершает
окно статусом `split`, `rejected` или `blocked_external`; третий прогон и
неограниченный возврат в review запрещены.

### Параллельный пакет подготовки

После P0 четыре потока идут параллельно по непересекающимся ownership zones:

| Поток | Владелец | Последовательность внутри потока | Выход в интеграцию |
| --- | --- | --- | --- |
| L — `W0-LOG-01` | OPS/logging | инвентарь трёх каналов → redaction contract → deny-by-default тесты → runbook/rollback | кандидат L1 без production-переключения |
| S — `W0-SEC-03` | OPS/API + владелец доступа | review fail-closed кода → список 3–4 сотрудников → уникальные hashes → защищённая выдача → rotation/revocation и rollback rehearsal | код + provisioning receipt; секретов в git/logs нет |
| O — `W0-OPS-02`, шаги 1–3 | OPS | зафиксировать kill-семантику watchdog → добавить liveness/readiness → прогнать shadow и измерить расхождения | shadow receipt; старый watchdog пока активен |
| E — интеграция | интегратор | заготовить матрицу CP1, команды проверки, rollback targets и сбор provenance | [матрица состояний](checkpoints/CP1_STATE_MATRIX.md) и [task cards](checkpoints/CP1_TASK_CARDS.md) L/S/O/E. Сам `CP1.json` заранее **не** выпускается даже как форма: по [checkpoints/README](checkpoints/README.md) квитанция коммитится отдельно и следующей за проверенным source commit, иначе возникает самоссылка |

Правила параллельности:

- общий workflow, реестр исключений и checkpoint receipt редактирует только
  интегратор;
- каждый поток сдаёт один reviewable commit и собственную первичку;
- production-состояние не меняется параллельными подготовительными работами;
- принятие ADR ведётся отдельно с WIP=1 и не блокирует подготовку CP1, если не
  меняет контракты redaction/auth/watchdog.

### Последовательный production rollout

1. **L2 — redaction первым.** Включить контракт, доказать, что секреты и
   чувствительные значения не попадают по умолчанию ни в diagnostic logs, ни в
   durable audit, ни в metrics. Зафиксировать наблюдение и rollback.
2. **S2 — auth вторым.** Только после завершённого provisioning проверить
   login/logout, cookie и WebSocket, liveness, fail-closed startup и rollback на
   production-like окружении; затем включить auth и закрыть `EXC-0001` фактом,
   а не готовностью к включению.
3. **O2 — watchdog последним.** Шаг 4 `W0-OPS-02` не выполняется в одну
   календарную неделю с S2. После чистого shadow-window атомарно переключить
   watchdog, проверить отсутствие kill-loop и лишь затем закрыть `/api/info`.

Любая утечка, локаут, расхождение liveness/readiness, ложное убийство процесса
или непроверенный rollback останавливает последовательность. Следующий rollout
не начинается, пока предыдущий не восстановлен либо не принят наблюдением.

## 4. Приёмка CP1

Интегратор собирает CP1 только после трёх production-результатов:

- `W0-LOG-01`: redaction действует, каналы разделены и негативные проверки
  чувствительных значений зелёные;
- `W0-SEC-03`: auth включён и fail-closed вне local mode, сотрудники получили
  индивидуальный доступ, rotation/revocation и rollback проверены,
  `EXC-0001` закрыто;
- `W0-OPS-02`: liveness/readiness наблюдались в shadow, watchdog переключён в
  отдельное окно, `/api/info` больше не служит health endpoint;
- merge commit достижим из актуального `origin/main`, CI и production-like
  smoke относятся именно к этому commit;
- `checkpoints/CP1.json` коммитится отдельно после проверенного source commit и
  содержит environment profile, test/evidence hashes, known defects, открытые
  исключения и production rollback targets.

`checkpoint_status` фиксирует фактическое состояние. `authorizes_next_cutover`
не становится `true` автоматически: это отдельный verdict соответствующего
gate. После CP1 следующим плановым шагом будет reconciliation G0, а не
автоматический старт W1.

## 5. Работы вне критического пути CP1

Чтобы не простаивать во время observation windows, отдельно и параллельно можно
готовить входы G0: решения `W0-DEC-01/02`, индивидуальную приёмку ADR с WIP=1,
production baseline `W0-OPS-01`, решения A-01…A-24, запуск timeout
`W0-STD-01`, первый недельный отчёт `W0-LEG-01`, golden fixtures и LLM replay.
Эти работы не подменяют три обязательных результата CP1 и не меняют их
production-порядок.
