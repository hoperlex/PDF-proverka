# Реестр архитектурных исключений

**Редакция:** 2026-08-27<br>
**Владелец реестра:** technical lead / интегратор программы

Здесь фиксируются только временные отклонения от принятой ADR Bible. Запись не
делает небезопасное состояние допустимым: если обязательный компенсирующий
контроль не подтверждён, применяется fail-closed и работа останавливается.

## EXC-0001. Legacy portal auth выключен по умолчанию

| Поле | Значение |
| --- | --- |
| Статус | active для legacy; не распространяется на новый control plane |
| Нарушаемый принцип | P-14, безопасность fail-closed |
| Область | `backend/app/core/portal_auth.py`, legacy portal и его текущий production deployment |
| Наблюдаемый факт | `PORTAL_AUTH_ENABLED` имеет default `false` |
| Причина | историческая совместимость и локальный режим до появления новой auth boundary |
| Риск | неаутентифицированный доступ к проектным данным и операциям при ошибке perimeter/configuration |
| Владелец | legacy production operator; контроль закрытия — интегратор программы |
| Истекает | 2026-10-15 либо до первого внешнего production canary — что наступит раньше |
| Задачи закрытия | `W0-SEC-01` threat model, `W0-SEC-03` legacy production auth rollout; `W0-ADR-06`/ADR-0010 отдельно проектирует AuthZ нового контура |

Обязательные компенсирующие контроли до закрытия исключения:

1. deployment доступен только через утверждённый private perimeter/reverse
   proxy; этот факт проверяется `W0-SEC-01`, а не предполагается;
2. опасные operator endpoints остаются fail-closed при выключенной portal auth;
3. состояние auth и попытки доступа видимы в журнале и мониторинге;
4. секреты и project payload не публикуются через liveness endpoint;
5. если private perimeter не подтверждён, исключение недействительно и auth
   включается до продолжения эксплуатации.

Критерий удаления EXC-0001: на фактическом legacy production deployment portal
auth включён, а startup policy вне явно обозначенного local/dev mode отклоняет
`false` и неизвестный auth state. Runbook проверяет login/logout, cookie/WS,
открытый liveness, rollback и отсутствие обхода защищённых routes.

До включения auth оператор подтверждает список трёх-четырёх сотрудников,
генерирует уникальные credentials/hashes вне репозитория и журналов, передаёт
начальные credentials по утверждённому защищённому каналу и получает
подтверждение входа. Runbook также задаёт owner, rotation и revocation. Общий
пароль или передача секрета через git/task tracker не закрывают исключение.

Object-level AuthZ нового write API остаётся обязательством ADR-0010 и Gate G2,
но не блокирует закрытие исключения о **полностью выключенной** legacy auth.
После выполнения `W0-SEC-03` запись переводится в `closed`, но не удаляется.

## EXC-0002. `ACTION_LOG_REDACTION=0` возвращает секреты и ПДн в вечный журнал

| Поле | Значение |
| --- | --- |
| Статус | active |
| Нарушаемый принцип | P-14 (fail-closed), P-13 (redaction как контракт) |
| Область | `backend/app/core/config.py` — флаг `ACTION_LOG_REDACTION`; аварийный режим `action_log` |
| Наблюдаемый факт | При `=0` журнал возвращается к дораздельному поведению: один файл, все поля дословно, включая секреты, presigned URL и ПДн, с ретеншном 180 дней |
| Причина | Redaction сама может оказаться дефектной и начать терять данные, нужные для разбора инцидента. Без выхода эксплуатация окажется в тупике: журнал есть, но бесполезен |
| Риск | Осознанное или забытое включение возвращает состояние, которое `W0-LOG-01` и устранял |
| Владелец | OPS (владелец журнала действий) |
| Истекает | не применимо: постоянный kill-switch, не feature flag |
| Пересмотр | при принятии ADR-0011 (observability/SLO) либо при появлении второго независимого канала диагностики |

Прежняя формулировка «§8 DoD п.10 закрыт» была преждевременной: п.10 требует
владельца и дату удаления, а отсутствие даты у постоянного kill-switch — это
отклонение, которое оформляется здесь, а не объявляется соответствием.

Обязательные компенсирующие контроли, пока исключение действует:

1. включение фиксируется в durable audit как административное действие с
   actor и причиной — состояние «журнал без redaction» не должно быть тихим;
2. включение допускается только при подтверждённом дефекте redaction и с
   парной задачей на починку; эксплуатация в этом режиме ограничена сроком
   разбора инцидента, а не оставляется до следующего релиза;
3. после возврата в `1` журналы, записанные в аварийном режиме, обрабатываются
   как класс из `W0-LOG-02` (классификация накопленного, ограничение доступа);
4. значение флага входит в `production startup checks`: старт в режиме `0` вне
   явно обозначенного разбора инцидента отклоняется.

Критерий закрытия: появляется второй канал диагностики, не требующий отключения
redaction, либо ADR-0011 фиксирует иную модель. После этого запись переводится
в `closed`, но не удаляется.
